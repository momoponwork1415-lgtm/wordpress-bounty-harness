# 提出候補の画面記録

原因グループを再生するときは、利用者が攻撃の前提から発火までを画像だけでも追えるように撮る。枚数は固定しない。途中に時間の経過や被害者の操作があれば、その前後を分ける。

1. 対象の版と初期状態、通常の設定画面、必要なデータを作る操作、その結果を順に撮る。脆弱性固有の前提（外部サービス接続、フォームやフィードの作成・保存など）は、サイト管理者が使う通常 UI と公式の外部フローで作る。UI が裏で発行する通信はその操作の一部だが、AI が `curl`、WP-CLI、内部 API、DB 書き込みを直接使って同じ状態を作るのは代替にならない。汎用的な Lab 初期化と、攻撃者が実際に送る HTTP は区別する。メール確認や接続コールバックが管理画面の nonce に結び付く場合は、開始時と同じ管理者セッションで完了させ、戻った先で接続結果を確認する。通常フローが止まったら理由を残し、直接操作で進めた試行はコード経路の調査として別に記録する。通常利用の再現が完了したと扱わない。
2. 攻撃前の被害者画面を撮る。攻撃者は別のブラウザ状態で操作し、権限・Cookie の有無、入力した値と送信先、実際の応答を記録する。HTTP 本文や応答は元データも Private Evidence に残す。
3. 保存先や定期処理を経由するなら、攻撃後の値と処理後の値を別々に記録する。DB や HTTP の値を読みやすく表示した自作画面は「診断用パネル」と明記し、プラグインの画面として扱わない。定期処理をラボ内で前倒しした場合は、その操作が攻撃者の手順ではないこと、通常は何を待つかを書く。
4. 被害者の画面と操作直前を撮り、実際の遷移・発火・発火後を撮る。alert を証拠にするならブラウザのネイティブなダイアログと URL が同時に見える全画面画像を残す。通常のページ撮影でダイアログが写らない場合は、使い捨て Lab の画面出力を撮る。Playwright で人間用ブラウザを起動する場合は、遷移前に `dialog` リスナーを付ける。リスナーがないと alert が自動で閉じられるため、見えなかったことを不発と判定しない。人間が確認するまでリスナーから dismiss せず、ブラウザイベントの種別・値・発火ページも元データとして残す。alert 以外の観測なら、その現象が分かる画面と対応するイベントを残す。
5. 画像を操作順に並べ、各画像に「誰が何をしたか／実画面か診断用か」を一文で付けた一覧を Git 外に作る。加えて、利用者が操作を監査できる表を作る。各行に操作主体、直前の画面、押したボタン・入力した値（秘密は伏せる）、遷移先と結果、対応する画像・記録、操作方法が通常 UI・攻撃者の HTTP・Lab 診断のどれかを書く。通常利用の前提をすべて列挙し、それぞれ UI で作ったか、迂回したか、未完了かを明記する。外部接続では公式サービスのホスト、メール送信、確認リンクを開いた事実、ドメイン確認、WordPress への復帰を別々に記す。サービスへの接続と外部アカウントの認証を混同せず、伏せた一時リンクで追跡できない部分は未監査と明記する。過去の内部 API による経路調査があれば、今回の通常 UI 再生と明確に区別する。Windows から開ける場所に原寸画像と一覧を置き、会話では一覧と重要な画像を直接示す。パスワード、メールの確認リンク、URL 内の nonce・接続トークン、セッション Cookie を画像・一覧に載せない。誤って写した画像は一覧から外し、Private Evidence からも除く。通常の接続や設定が終わる前に撮影を止めた場合は、未完了として記録し、提出用の再現証拠に昇格させない。

これらの画面記録は人間の理解とレビューのための観測であり、Harness の `runtime-confirmed` 判定を代替しない。
