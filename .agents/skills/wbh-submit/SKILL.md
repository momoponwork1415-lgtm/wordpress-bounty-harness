# 対話型の提出セッション

利用者はこの入口だけを呼ぶ。段階ごとの `wbh-*` スキルは必要な資料として読み、利用者に個別の呼び出しを求めない。一件が終わって「次」と言われたら、同じ会話で最新の一覧から次の Finding を選ぶ。

## セッションの開始・再開

1. repository、Harness state、対象 campaign を確認する。既に会話で固定したものは再質問しない。`harness review --campaign <id>` と各 `review export`、既存の非公開判断・提出記録を読み、現時点の queue を作る。探索を新たに走らせない。必要な段だけ、repo の `.claude/skills/wbh-screen`、`wbh-verify`、`wbh-review`、`wbh-dedupe`、`wbh-destination`、`wbh-report` を参照する。
2. Programme Boundary の parked、提出しないと決めたもの、提出済みのものを、次候補の表示から外す。利用者が明示的に一覧を求めたときだけ別に見せる。歴史的な記録は消さない。Harness の正式な状態と、利用者が会話で伝えた提出済み事実を混同しない。
3. 残る Finding を一括で安く選別する。`wbh-screen` の現行版と Wordfence 規則の写しを読み、**明示的な除外条項に、独立に確認した事実が直接一致するものだけ**を分ける。公開ミラーの類例が 0 件、`incomplete`、短い時間窓、競合、特別な設定、最初の数人に限る表示という名前だけでは落とさない。
4. 残りを前提の軽さ、最終影響、最新版との関係で短い候補表にする。対象が多ければ、上位数件と残件数だけ見せる。利用者が「次」と言ったら、既に見送った候補を再表示せず、次を進める。

## Finding 一件のループ

1. **前提を議論する。** 固定 source と WordPress.org / 開発元の公式資料で、プラグインの主用途、必要な管理者設定、攻撃者・被害者の役割と行動、時間制限や到達範囲を調べる。「普通の公開サイトがこの設定を使うか」は人間と議論し、AI の推測だけで棄却しない。資料だけで答えが出なければ、小さい Lab 観測を行ってから議論に戻る。全件の議論完了を待って検証を始める必要はない。
2. **発火まで再生する。** 選んだ Finding は固定 Snapshot の使い捨て gVisor Lab だけで対象を実行する。通常の画面操作で前提を作り、攻撃者の位置から payload を入れ、別の被害者セッションで必要な画面と操作をたどる。攻撃前、入力・送信、被害者の遷移、発火を、順番が分かる全画面画像とブラウザイベントで記録する。動画は任意。画像は利用者が実際に開ける場所・方法で示す。既存コンテンツからの発火と取り違えないよう、清潔な開始状態、捕捉した攻撃要求、後続の被害者訪問を対応させる。
3. **一画面で説明する。** 何のプラグインか、今回の設定は通常用途か、攻撃者が何をどこに入れたか、payload、被害者が何をしたか、何が発火したか、入力から sink までの脆弱なコード、残る不確実性を短く示す。必要なコード断片と攻撃文字列は利用者が理解できるよう会話に表示する。観測した事実と source からの推論を分け、alert の画像だけで因果関係を断定しない。
4. **利用者の判断を記録する。** 画像と説明を提示してから「報告へ進む／追加検証／提出しない」を尋ねる。利用者の判断が既に会話にあれば繰り返し聞かない。環境・手順・観測の失敗は Finding の否定にせず、何が足りないかを残す。却下理由は個別の事例として残し、別の候補へ一律に広げるのは複数の事例と公式規則で支えられるときだけにする。
5. **報告を準備する。** 利用者が進めると決めたら、公開済み重複、最新の配布版、Wordfence の対象範囲を照合する。同じ根本原因の別 sink や既存提出との関係を確認する。Wordfence 履歴 mirror の近い受理例は文体と必要な要素の参考にし、本文を写さない。証拠の範囲内で短い英語の報告書とフォーム入力用 JSON を作り、本文を会話で見せる。下書きは Git 外に置き、利用者が確認した提出用 JSON は Windows から見える報告フォルダへ置く。拡張機能用 JSON に内部状態を入れない。最新版や影響範囲を観測以上に広げない。
6. **次へ回す。** 利用者が提出したと伝えたら、送信した事実だけを非公開で記録する。チケット番号は要求しない。Harness の正式な `submitted` イベントを作れない場合は、その違いを記録する。最新の queue を読み直し、次候補とその前提を示して同じ会話で続ける。利用者が止めた場合はそこで終える。

## 境界

- `runtime-confirmed` は nonce canary を照合した Harness 判定器だけが出す。`incomplete` は偽陽性の判定ではない。画像や dialog をそのラベルに読み替えない。
- 現行の `review draft` / Submission Candidate が視覚的な観測を正式な根拠として受け付けない場合、対応する正式状態を偽装しない。非公開の下書きと観測として提示し、欠けるゲートを明示する。SPEC・ADR・Review API の変更はこのスキルとは別に行う。
- payload、HTTP 本文、認証情報、未公開 Finding、画像、実行ログは Git・公開 Issue・PR に置かない。Private Evidence は Git 外に置き、利用者向けの表示では資格情報を伏せる。
- 外部フォームへの入力・送信、vendor への連絡、公開は自動で行わない。最終文案・入力値の確認と送信は利用者が行う。
