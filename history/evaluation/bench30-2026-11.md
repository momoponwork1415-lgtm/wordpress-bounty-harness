# bench30（2026-11）: 既知の公開脆弱性を持つ版での探索 benchmark

探索の変更を本番の雑音なしで較正するための一覧である（Issue #726）。現行は **v3（密な版、2026-11-01 夜）** で、v1（10k 以上、1 版 1 答）の記録は末尾に残す。v2（50k 以上、1 版 1 答）は選定と答えまで作ったが回さずに v3 に置き換えた。A/B/C の定義は [docs/reviews/2026-11-01-noticing-vs-reasoning.md](../../docs/reviews/2026-11-01-noticing-vs-reasoning.md) の「分類の基準」に従う。この文書には Git に入れてよい情報（slug、版、CVE、型、公開日、インストール数、zip の sha256）だけを書く。答え（脆弱なファイルと関数）、zip、展開したソースは Git の外に置く（不変条件 8、#678）。この一覧と答えは探索の入力にしない（不変条件 1）。採点は Trial が終わった後に、台帳と答えを突き合わせて行う。

## v3 の考え方（所有者決定 2026-11-01）

- **インストール数 50,000 以上**。v1 の 10,000 以上は、報酬の出る対象の帯から外れていた（所有者 2026-11-01「せめて 50k 以上」）。
- **1 つの版に複数の脆弱性**。所有者の実績（TranslatePress 3.2.6 で複数件）に合わせ、1 プラグインにつき、Wordfence の 2026 年公開記録（対象範囲内）が最も多く当たる WordPress.org の版を「密な版」として選ぶ。3 件以上当たる版に限る。1 Trial で当たりが複数あるので、「探索が何かを拾えたか」を 1 版で測れる。
- 密な版は古い版である。本番は最新版を探索するので、v3 の再発見率は本番より高めに出る。報告では「密な版の benchmark」と明記し、本番の Lab-fire 率と混ぜない。
- 30 本の内訳: A 群 12 本（A の記録が 2 件以上ある版）、C 群 8 本（C の記録が 1 件以上。該当する版はこれで尽きた）、B 群 10 本（B の記録が 3 件以上）。記録は 198 件（A 53、B 125、C 20）、未認証 156 件。インストール数は 100,000 以上が 17 本、中央値 100,000。

## v3 の選定の基準

- 出所: Wordfence 履歴 mirror（`history.sqlite`、最新の公開日 2026-10-30）の 2026 年公開記録。1 記録 1 プラグイン、CVE があり、修正版が出ているもの。種類と攻撃者の位置の条件は v1 と同じ（Programme Boundary 内、未認証か Subscriber+ / Customer 同等だけ）。
- インストール数: WordPress.org の `active_installs` が 50,000 以上（2026-11-01 に API で確認）。
- 版: WordPress.org の版付き tag のうち、対象範囲内の記録が最も多く当たる版（同数なら新しい方）を「脆弱な版」にする。各記録の答えは「その記録の最終影響版 → 最初の修正版」の 1 リリース差分から取り、脆弱な版のソースで同じ箇所があることを確かめる。脆弱な版に無い記録は答えに `presentInVuln: false` を付け、再発見率の分母から外す。
- 修正腕: 全記録が修正された最小の版（各記録の修正版の最大）を 1 Trial 回し、偽陽性を見る。
- 主答: 群と同じ型で脆弱な版に存在する記録のうち、答えの confidence が高いものを優先し、次に未認証、次に CVSS で選ぶ。pass@k は「どの記録でも当たり」と「主答に当たり」の 2 つを出す。
- 答えの出来（2026-11-01）: 198 記録のうち、脆弱な版に存在 192、存在しない 6（tutor 3、user-registration 2、wp-slimstat 1。分母から外す）。confidence は high 99 / medium 69 / low 30。主答 30 件は high 26 / medium 3 / low 1（jetformbuilder）。同じ修正リリースを共有する記録は同じ箇所を指すことがあり、record recall はその分だけ甘くなる。
- 除外は v1 と同じ（自分たちが提出したプラグイン、所有者が研究者に入る記録）。
- 30 本とも root 直下にヘッダ付き PHP が 1 つだけで、#734 の遅延には当たらない。translatepress-multilingual と customer-reviews-woocommerce は WooCommerce の版ヘッダだけを持つ（任意の依存、固定なしで `header-derived-unpinned`）。`Requires Plugins` を持つものは無い。

## 採点の手順（読み取り専用）

### Trial の回し方との対応

- 1 件につき、脆弱な版で 3 Trial、修正版で 1 Trial を回す（Issue #726）。各 Trial は別の campaign にし、campaign id に benchmark の接頭辞を付ける（例: `bench30-<slug>-vuln-1`、`bench30-<slug>-fixed-1`）。benchmark の campaign は選定を通さず、funnel の分母に入れない。
- 答えの JSON はどの Trial にも渡さない。採点は、その case の全 Trial が終わってから行う。

### 突き合わせ

1. campaign と case の対応表を Git 外に作る: `{"<campaignId>": {"cve": "CVE-...", "arm": "vulnerable" | "fixed"}, ...}`。
2. `node --no-warnings score.mjs --state <state> --map <map.json>` を実行する。スクリプトは `<state>/ledger.sqlite` を `readOnly` で開き、campaign ごとに `finding-recorded`、`finding-parked`、`lead-recorded` を読む。各 event の `artifacts` の `finding`（`lead`）の digest から `<state>/private-evidence/<digest>/content/finding.json`（`lead.json`）を読み、`sourceTrace` の各 frame の `file` と `function` を答えと比べる。台帳にも Private Evidence にも書かない。
3. 比べ方:
   - ファイル: 先頭の `/workspace/main/`、`./`、`<slug>/` を外した相対パスが答えのファイルと一致するか、どちらかが他方の末尾に一致すれば当たり。
   - 関数: `Class::method`、`->method`、`.method` の最後の名前を小文字にして、答えの関数名と一致すれば当たり。
4. 判定:
   - **ソース水準の再発見**: 脆弱な版の Trial の Finding（`finding-recorded` か `finding-parked`）の `sourceTrace` が、答えのファイルか関数に 1 frame でも届いたもの。関数まで届いたものは「関数水準」として別に数える。
   - **pass@3**: 脆弱な版の 3 Trial のどれかで再発見があれば、その case は 1。型ごとに「pass@3 の case 数 / 10」を出す。
   - **Lead だけ**: Finding では届かず、Lead の `sourceTrace` だけが届いた case。再発見には数えず、別の列で出す。
   - `incomplete` で終わった Trial と、artifact を読めなかった Finding（`missingArtifacts`）は、再発見なしに混ぜない。Trial 数と一緒に報告する。
5. スクリプトの当たりは候補である。impact の種類が記録と同じか（例: SQLi の case で SQLi の Finding か）を、Finding の `impact` と `claim` を読んで AI が確かめ、違えば当たりから外す。外した件数も報告する。

### 修正版での偽陽性の数え方

- 修正版の Trial の Finding のうち、`sourceTrace` が答えのファイルか関数に届き、impact の種類が記録と同じものを **偽陽性** に数える。修正済みの箇所を、修正前と同じ主張で報告したことになるからである。
- 型ごとの偽陽性率は「偽陽性が 1 件以上あった case 数 / 修正版の Trial を回した case 数」とする。Finding 単位の件数も併記する。
- 修正版の Trial で、答えの場所に届かない Finding は偽陽性に数えない。未知の脆弱性か別の誤りかは benchmark では判定できないので、「修正版のその他の Finding」として件数だけ出す。
- 修正版の Trial が `incomplete` なら、その case は偽陽性率の分母から外し、外した数を書く。

### 報告に書くもの

型ごとの pass@3 再発見率、関数水準の率、Lead だけの case 数、修正版での偽陽性率、1 件あたりの Codex 時間（`discovery-run-finished` の wall）。Issue や PR には件数と CVE だけを書き、答えのファイル名・関数名・Finding の本文は書かない。
