# 探索後のスキルと検証経路の整理（2026-10-25）

## 問いと参照した状態

探索後の Finding を、通常利用での成立可能性、実際の発火、原因、提出文案まで少ない手戻りで渡せるか。現作業ブランチ `wbh-verify-v8` は `origin/main` より 35 commit 古い。以下の現行運用の評価はローカル `origin/main` の六つの `.claude/skills/wbh-*` と SPEC、ADR 0038 を基準にする。作業ブランチの `wbh-screen v2.2` / `wbh-report v3` は現行運用の基準にしない。

## 観測した事実

- `origin/main` の `wbh-screen v4` は、Wordfence 規則と独立に確認した事実が直接一致する明示除外だけを検証列から外す。ミラーに類例が 0 件、短い時間窓、競合、通常構成の不明という理由だけでは外さない。旧版の一律判断はすでに修正されている。
- `wbh-verify` は gVisor Lab の前提作り、攻撃者位置の実行、被害者側観測を扱うが、六ファイルの handoff と canary を中心に組み立てられている。数値 alert のブラウザ観測も補助証拠として保存できる。
- `wbh-review` は `incomplete` なら `defer` を提案して終わり、人間向けの会話に payload、HTTP 本文、未公開 Finding の中身を載せない。画面、原因、攻撃文字列を見て判断する今回の対話とは合わない。
- `wbh-report v7` は `runtime-confirmed` からの正式な暫定文案と JSON を認める。一方、`incomplete(observation)` に実際のブラウザ dialog が記録されたケースは内部プレビューに留まり、正式な draft / Submission Candidate に進めない。人間の手動 Lab 再現を最終ゲートとする。
- 今回の一件では、使い捨て Lab と実ブラウザで発火を観測し、コード・攻撃の順序・通常用途を対話で説明して、所有者が文案を確認し提出した。形式上の判定は `incomplete(observation)` のままであり、現行の正式な提出経路では表せない。これを `runtime-confirmed` と呼び替えることもできない。
- SPEC 第 2 節では `runtime-confirmed` の発行主体、Snapshot digest、Private Evidence、外部行動承認が不変条件である。SPEC 第 3・8 節と ADR 0038 は人間の手動再現を提出経路に置いている。判定器の削除または手動再現ゲートの変更はスキルだけでは完結しない。

## 提案する人間向け経路

1. `review` 一覧を出し、Programme Boundary の既存 park と `wbh-screen v4` の明示除外を適用する。曖昧な通常構成、時間窓、競合、被害者の操作条件は「確認点」として残し、脆弱性が無いという判断にはしない。
2. 候補ごとに固定 Snapshot の gVisor Lab を起動する。通常の管理画面操作で前提を作り、攻撃者の権限から payload を入力する。攻撃前、送信後、被害者の操作、発火時の**全画面**を順に撮る。画面画像、ブラウザの dialog event、捕捉した攻撃要求、固定ソースの該当箇所を Git 外の Private Evidence に保存する。動画は任意とする。
3. 説明は「プラグイン本来の目的 → 前提となる設定と通常性 → 攻撃者の入力と payload → 被害者が実際にする操作 → 起きた結果 → 入力から出力までのコード → 残る不確実性」の順に短く示す。対話では人間に読ませるための必要な payload とコード断片を表示できるようにする。Git、公開 Issue、PR には載せない。
4. 既存コンテンツの発火を取り違えないため、清潔な Lab の攻撃前状態と攻撃後状態を区別し、被害者セッションと攻撃者セッションを分ける。画像一枚、Verifier の自己申告、alert の表示だけから因果関係を断定しない。設定、版、要求、ブラウザイベントを同じ Snapshot / attempt に結ぶ。
5. 所有者は画像と説明を見て、通常用途として納得できるか、追加確認が要るか、提出対象から外すかを対話で決める。UI や Lab の失敗は Finding の否定にしない。過去の却下事例は却下理由・前提・通常用途を記録し、別の対象にも成り立つ条件だと確認できたものだけ選別スキルへ反映する。
6. 最新版、公開済み重複、Wordfence scope を照合し、英語の短い報告書と拡張機能入力用 JSON を作る。所有者が画面証拠・文案・フォーム入力を査読し、外部送信を行う。提出後のチケットと転帰は別に記録する。

短い時間窓、競合、最初の数人に限る表示、特別なフォームは一律の技術的反証ではない。被害者が通常どう到達するか、成立する頻度、管理者がその機能を通常使う理由を個別に示せない場合、提出優先度を下げるか所有者の対話判断に回す。単一の却下票を恒久的な除外規則にしない。

## 六つのスキルの処遇案

| 現在のスキル | 現在の役割 | 推奨 |
| --- | --- | --- |
| `wbh-screen v4` | 明示除外と検証列への振分け | 維持。曖昧な前提は確認点として書く。実際の却下から学ぶときだけ狭い除外例を追加。 |
| `wbh-verify` | Lab handoff、攻撃、canary とブラウザ観測 | 大幅改訂。ブラウザ再生と段階的な全画面画像・コード根拠・通常用途の説明を主成果物にする。canary は任意の追加診断に下げる案。 |
| `wbh-review` | 状態の要約と accept / reject / defer 提案 | `wbh-verify` の人間向け説明に統合する案。最終判断と台帳記録は独立した薄い手順として残す。 |
| `wbh-dedupe v2` | 公開済み重複の調査 | 維持。根本原因が同じ複数 sink のまとめ方もここで確認する。 |
| `wbh-destination v1` | Wordfence / Patchstack / vendor の選択 | 当面の Wordfence 主経路では `wbh-report` に統合する案。他の提出先へ実際に出す時に独立運用を再評価。 |
| `wbh-report v7` | Wordfence 文案・JSON と厳格な登録ゲート | 改訂。観測した事実と未解決点を分けた文案・JSON を作り、人間の査読へ渡す。正式登録条件の変更は SPEC / ADR / Review API と同時に扱う。 |

これにより主経路は `screen → verify（再生＋人間向け説明＋判断）→ dedupe → report（提出先確認を含む）` の四技能にできる。ただし機能を消す前に、履歴の読取り、台帳、外部送信承認が保たれることを確認する。

## 判断が必要な点と変更順

1. **判定器を主経路の必須条件から外すか。** 推奨は「まず提出準備のゲートから外し、`runtime-confirmed` の定義と過去の記録は保持」。判定器コードそのものの削除は、その利用箇所と履歴互換を測って別に決める。`incomplete` を真偽の否定には使わない。
2. **人間の最終確認を画面・コード・文案の査読に変えるか。** 変えるなら、現在の「人間が Lab で手動再現して `match`」という正式な条件を SPEC、ADR 0038、Review API、`wbh-report` で整合させる。Wordfence フォームの Certification は実際に確認した範囲に限り正確に答える。
3. 上記を所有者が決めたら、DEVELOPMENT 第 6 節の順序（報告 → 所有者決定 → ADR → PR）で変更する。最初の PR は一件の Finding で段階画像、説明、Wordfence 文案、JSON、所有者査読まで通す縦断スライスにする。探索ランナーは触らない。

この文書は調査報告であり、SPEC、ADR、スキル、判定器、提出状態を変更しない。
