```markdown
# 対話型の提出セッション

利用者はこの入口だけを呼ぶ。段階ごとの `wbh-*` スキルは必要な資料として読み、利用者に個別の呼び出しを求めない。一件が終わって「次」と言われたら、同じ会話で最新の一覧から次の Finding を選ぶ。

## セッションの開始・再開

1. repository、Harness state、対象 campaign を確認する。既に会話で固定したものは再質問しない。`harness review --campaign <id>` と各 `review export`、既存の非公開判断・提出記録を読み、現時点の queue を作る。探索を新たに走らせない。必要な段だけ、repo の `.claude/skills/wbh-screen`、`wbh-verify`、`wbh-review`、`wbh-dedupe`、`wbh-destination`、`wbh-report` を参照する。
2. Programme Boundary の parked、提出しないと決めたもの、提出済みのものを、次候補の表示から外す。利用者が明示的に一覧を求めたときだけ別に見せる。歴史的な記録は消さない。Harness の正式な状態と、利用者が会話で伝えた提出済み事実を混同しない。
3. 残る Finding を一括で安く選別する。`wbh-screen` の現行版と Wordfence 規則の写しを読み、**明示的な除外条項に、独立に確認した事実が直接一致するものだけ**を分ける。公開ミラーの類例が 0 件、`incomplete`、短い時間窓、競合、特別な設定、最初の数人に限る表示という名前だけでは落とさない。
4. 残りの Finding を報告前に束ねる。同じ対象・Snapshot で、攻撃者入力、壊れた信頼境界、共通の原因コードが同じなら原因グループとし、Finding ID と sink を全件並べる。同じ `impact` label や同じ画面というだけでは束ねない。既存の group 情報は手掛かりにし、固定 source で照合する。既に提出したグループに新しい sink があれば新規報告でなく追記候補にする。
5. 原因グループを前提の軽さ、最終影響、最新版との関係で短い候補表にする。対象が多ければ、上位数グループと残件数だけ見せる。利用者が「次」と言ったら、既に見送った候補を再表示せず、次を進める。

## 原因グループ一件のループ

1. **前提を議論する。** 固定 source と WordPress.org / 開発元の公式資料で、プラグインの主用途、必要な管理者設定、攻撃者・被害者の役割と行動、時間制限や到達範囲を調べる。「普通の公開サイトがこの設定を使うか」は人間と議論し、AI の推測だけで棄却しない。資料だけで答えが出なければ、小さい Lab 観測を行ってから議論に戻る。全件の議論完了を待って検証を始める必要はない。
2. **発火まで再生する。** 選んだグループの代表から、固定 Snapshot の使い捨て gVisor Lab だけで対象を実行する。脆弱性固有の前提は通常の画面操作と必要な外部接続で作り、攻撃者の位置から payload を入れ、別の被害者セッションで必要な画面と操作をたどる。前提を直接 HTTP・CLI・DB 操作で代替した試行は、通常導線の再現と扱わない。発火までの各操作を、前提・攻撃・被害者の順に全画面画像とブラウザイベントで記録する。撮影の具体的な手順は [画面記録](references/visual-evidence.md) に従う。動画は任意。既存コンテンツからの発火と取り違えないよう、清潔な開始状態、捕捉した攻撃要求、後続の被害者訪問を対応させる。保存や HTML 到達だけで止めず、クリックやホバーを含む被害者の通常操作と最終描画後の処理まで観測する。対象が依存するプラグインやブラウザが実行を止める場合は、その版と止まった箇所を記録する。別 sink も一つずつ確認し、未確認のものを発火済みと書かない。
3. **攻撃経路と原因を説明する。** 何のプラグインか、今回の設定は通常用途か、攻撃者が何をどこに入れたか、payload、被害者が何をしたか、何が発火したか、共通の原因コードと sink ごとの差、残る不確実性を最初に短く示す。実際の画面操作と調査用の操作を区別し、具体的な入力値が「HTTP 項目 → 保存先 → 後続処理 → 最終画面」のどこを通ったか順に示す。定期処理やキャッシュなど、経路の理解に必要な語はその場で平易に説明する。管理者と一般訪問者など被害者ごとの確認済み経路を区別する。原因箇所の実コードをファイル・行番号付きで会話に表示し、入力がどこでエスケープされ、どの後続処理で信頼境界を越えるかを説明する。攻撃文字列の各部分が担う役割も示す。観測した事実と source からの推論を分け、alert の画像だけで因果関係を断定しない。利用者が経路やコードを理解する前に報告文案だけを提示して終えない。
4. **利用者の判断を記録する。** 画像と説明を提示してから「報告へ進む／追加検証／提出しない」を尋ねる。利用者の判断が既に会話にあれば繰り返し聞かない。環境・手順・観測の失敗は Finding の否定にせず、何が足りないかを残す。通常操作で発火しなかった場合は、保存・出力・最終処理のどこまで確認したかと提出見送りの判断を分けて記録し、`incomplete` を勝手に `contradicted` や全経路の偽陽性へ変えない。却下理由は個別の事例として残し、別の候補へ一律に広げるのは複数の事例と公式規則で支えられるときだけにする。
5. **報告を準備する。** 利用者が進めると決めたら、公開済み重複、最新の配布版、Wordfence の対象範囲を照合する。原因グループの全 Finding ID と各 sink の証拠を確認し、同じ原因を一つの報告書にまとめる。既存の提出と同じ原因なら、新規報告ではなく追記案を作る。原因の同一性が曖昧なら利用者と決める。Wordfence 履歴 mirror の近い受理例は文体と必要な要素の参考にし、本文を写さない。証拠の範囲内で短い英語の報告書とフォーム入力用 JSON を作る。報告書はタイトル、説明、影響、再現手順、環境、参照先まで全文を会話に表示する。リンクや要約だけで済ませず、修正した場合も最新版の全文を再掲して JSON の入力値との一致を確認する。下書きは Git 外に置き、利用者が確認した提出用 JSON は Windows から見える報告フォルダへ置く。拡張機能用 JSON に内部状態を入れない。最新版や影響範囲を観測以上に広げない。
6. **次へ回す。** 利用者が提出したと伝えたら、送信した事実だけを非公開で記録する。Windows 側の提出管理フォルダでは対象を未提出から提出済みへ移し、索引の日付と状態を更新する。チケット番号は要求しない。証拠は保持し、使い捨て Lab と一時資格情報を片付ける。Harness の正式な `submitted` イベントを作れない場合は、その違いを記録する。最新の queue を読み直し、次候補とその前提を示して同じ会話で続ける。利用者が止めた場合はそこで終える。

## 境界

- `runtime-confirmed` は nonce canary を照合した Harness 判定器だけが出す。`incomplete` は偽陽性の判定ではない。画像や dialog をそのラベルに読み替えない。
- 現行の `review draft` / Submission Candidate が視覚的な観測を正式な根拠として受け付けない場合、対応する正式状態を偽装しない。非公開の下書きと観測として提示し、欠けるゲートを明示する。SPEC・ADR・Review API の変更はこのスキルとは別に行う。
- 既存の `wbh-report` はフォーム項目と正式な draft 条件の参考に留める。同スキルの 1 Finding 1 下書きや本文を会話に出さない出力規則を、この対話型セッションの私的な報告案へ持ち込まない。同根の複数 Finding を一報告へ束ねる非公開の文案を先に作り、正式な draft がその全件に結び付かないなら結び付いたと主張しない。
- payload、HTTP 本文、認証情報、未公開 Finding、画像、実行ログは Git・公開 Issue・PR に置かない。Private Evidence は Git 外に置き、利用者向けの表示では資格情報を伏せる。
- Wordfence などの脆弱性報告フォームへの入力・送信、vendor への連絡、公開は自動で行わない。最終文案・入力値の確認と送信は利用者が行う。通常利用の前提となる外部サービス接続は、利用者が許可したアカウントと通信範囲で行う。
```

```markdown
# 提出候補の画面記録

原因グループを再生するときは、利用者が攻撃の前提から発火までを画像だけでも追えるように撮る。枚数は固定しない。途中に時間の経過や被害者の操作があれば、その前後を分ける。

1. 対象の版と初期状態、通常の設定画面、必要なデータを作る操作、その結果を順に撮る。脆弱性固有の前提（外部サービス接続、フォームやフィードの作成・保存など）は、サイト管理者が使う通常 UI と公式の外部フローで作る。UI が裏で発行する通信はその操作の一部だが、AI が `curl`、WP-CLI、内部 API、DB 書き込みを直接使って同じ状態を作るのは代替にならない。汎用的な Lab 初期化と、攻撃者が実際に送る HTTP は区別する。メール確認や接続コールバックが管理画面の nonce に結び付く場合は、開始時と同じ管理者セッションで完了させ、戻った先で接続結果を確認する。通常フローが止まったら理由を残し、直接操作で進めた試行はコード経路の調査として別に記録する。通常利用の再現が完了したと扱わない。
2. 攻撃前の被害者画面を撮る。攻撃者は別のブラウザ状態で操作し、権限・Cookie の有無、入力した値と送信先、実際の応答を記録する。HTTP 本文や応答は元データも Private Evidence に残す。
3. 保存先や定期処理を経由するなら、攻撃後の値と処理後の値を別々に記録する。DB や HTTP の値を読みやすく表示した自作画面は「診断用パネル」と明記し、プラグインの画面として扱わない。定期処理をラボ内で前倒しした場合は、その操作が攻撃者の手順ではないこと、通常は何を待つかを書く。
4. 被害者の画面と操作直前を撮り、実際の遷移・発火・発火後を撮る。alert を証拠にするならブラウザのネイティブなダイアログと URL が同時に見える全画面画像を残す。通常のページ撮影でダイアログが写らない場合は、使い捨て Lab の画面出力を撮る。Playwright で人間用ブラウザを起動する場合は、遷移前に `dialog` リスナーを付ける。リスナーがないと alert が自動で閉じられるため、見えなかったことを不発と判定しない。人間が確認するまでリスナーから dismiss せず、ブラウザイベントの種別・値・発火ページも元データとして残す。alert 以外の観測なら、その現象が分かる画面と対応するイベントを残す。
5. 画像を操作順に並べ、各画像に「誰が何をしたか／実画面か診断用か」を一文で付けた一覧を Git 外に作る。加えて、利用者が操作を監査できる表を作る。各行に操作主体、直前の画面、押したボタン・入力した値（秘密は伏せる）、遷移先と結果、対応する画像・記録、操作方法が通常 UI・攻撃者の HTTP・Lab 診断のどれかを書く。通常利用の前提をすべて列挙し、それぞれ UI で作ったか、迂回したか、未完了かを明記する。外部接続では公式サービスのホスト、メール送信、確認リンクを開いた事実、ドメイン確認、WordPress への復帰を別々に記す。サービスへの接続と外部アカウントの認証を混同せず、伏せた一時リンクで追跡できない部分は未監査と明記する。過去の内部 API による経路調査があれば、今回の通常 UI 再生と明確に区別する。Windows から開ける場所に原寸画像と一覧を置き、会話では一覧と重要な画像を直接示す。パスワード、メールの確認リンク、URL 内の nonce・接続トークン、セッション Cookie を画像・一覧に載せない。誤って写した画像は一覧から外し、Private Evidence からも除く。通常の接続や設定が終わる前に撮影を止めた場合は、未完了として記録し、提出用の再現証拠に昇格させない。

これらの画面記録は人間の理解とレビューのための観測であり、Harness の `runtime-confirmed` 判定を代替しない。
```
