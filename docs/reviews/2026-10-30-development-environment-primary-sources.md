# 開発環境整備の一次資料メモ（2026-10-30）

調べて報告。正本ではなく、規則や承認条件を追加する文書ではない。対象は Harness を開発する工程である。[SPEC](../SPEC.md)、該当 ADR、[DEVELOPMENT](../DEVELOPMENT.md)、[LESSONS](../LESSONS.md)、[PARKING](../PARKING.md) と照合した。記事の提案を、そのまま脆弱性探索・成立判断の仕様にはしない。

## 記事で確認できたこと

- [Anthropic「How the Claude Code team does code review」](https://claude.dev/blog/solving-code-review-at-anthropic/)（Addy Osmani、Morgan Westlee Lunt、Qing Wang、2026-10-15）。チームは 6〜9 月に merged PR が倍以上になり、revert の割合が 40% 超下がったと報告する。検証出力、別コンテキストのレビュー、短い `REVIEW.md`、CI、復旧を組み合わせる。再レビューは 3 巡後に方針を見直し、その後の差分に絞り、重複指摘を避ける。目的は revert・incident を増やさず人間の作業時間を減らすこと。これは当事者の運用報告で、どの施策が改善を生んだかを単独で証明する比較実験ではない。
- [O’Reilly「Software Factories, Light and Dark」](https://www.oreilly.com/radar/software-factories-light-and-dark/)（Addy Osmani、2026-09-18）は、[本人の原著](https://addyosmani.com/blog/software-factories/)（2026-07-20）の転載。主張は、安価で信頼できる検証の範囲に自律性を合わせ、長期の設計判断と結果の責任を人間が持つこと。型、モジュール境界、短い作業単位がその支えになる。全自動開発の普遍的な失敗率を示した研究ではなく、経験に基づく論考として扱う。

## この repo への適用案

以下は記事と現状を照合した提案で、採用済みの規則ではない。

1. **既存の入口を揃える。** Issue、小さな変更、`pnpm check`、merge、運転確認の基盤は既にある。独立レビューの実行と収束は手順に明記する必要がある。新しい orchestrator を導入する前に、[PR 手順](../agents/pr-review-merge.md)と[テンプレート](../../.github/pull_request_template.md)を正本へ合わせる。両方が探索変更に旧「開発 6 case × 3 run」を要求する一方、DEVELOPMENT §5 は本番比較を既定とし、開発セットへ戻す条件を限定している。
2. **レビューの出口を短くする。** レビュー観点を追加する場合は、既存 PR 手順を正本にして短い `REVIEW.md` から参照する。各指摘に変更で生じる不具合、根拠の場所、再現・検査方法を求める。再レビューの回数と対象差分を記録し、同じ指摘の言い換えで修正を増やさない。まず少数の実 PR で有効な指摘数、誤指摘、巡回数を測る。
3. **検証の証拠と戻し方を先に用意する。** 実行コマンド・結果・対象 commit を PR に結び付ける。CI の成功だけで本番の健全性を推定せず、影響する運転経路と復旧手順を短く書く。台帳は追記専用なので、コードの revert と記録の互換性は別に確認する（SPEC §2・§5）。
4. **増やす前に測る。** PR の待ち時間・レビュー時間・修正巡回数に、merge 後の不具合と revert を添える。計測は既存 Issue・PR の記録から始める。既に「open PR が 3 本を超えたら新規実装 PR を出さない」逆圧があるため、別の作業列やダッシュボードを先に作る必要はない（PR 手順「逆圧」、LESSONS 8・13）。

## 安定運用の設計根拠（所有者の 2026-10-30 の指示を反映）

この 2 記事を、必要な道具の一覧と安定運用の設計を結ぶ根拠にする。O’Reilly は自律性をどこまで許すか、Anthropic は変更をどう検査・レビュー・復旧するかの参考になる。以下の適用と確認方法は、このリポジトリ向けの提案であり、記事の実績でも、導入済みの機能でもない。

| 記事から採る原則 | このリポジトリで具体化すること | 確認方法 |
| --- | --- | --- |
| 検証できる範囲に自律性を合わせる（O’Reilly） | 工程ごとに入力、完了の根拠、失敗時の行き先を決める。既存の PR 数上限と承認境界を使う。 | CI 失敗、計測不足、レビュー未完了から、完了扱いや次の変更へ進まないことを確認する。 |
| 実行可能な証拠と独立レビューを使う（Anthropic） | コマンド、結果、対象 commit を結び付け、実装と別の文脈で仕様と差分を読む。 | テスト 0 件を失敗にする。確認した head と取り込む head の一致を確認する。 |
| レビューを収束させる（Anthropic） | 初回のレビュー後は修正差分と未解決項目に焦点を当てる。3 巡で方法を再考する。 | 各指摘の修正または理由付き解消を記録する。3 巡は自動承認や不具合の無視を意味しない。 |
| 理解できる構造を保つ（O’Reilly、Anthropic） | 型・公開境界・用語を揃え、変更する部分の目的と影響範囲を説明できるようにする。 | 境界検査と受入試験を使う。古い手順書を正本へ揃え、重要な設計判断をテストの緑だけで済ませない。 |
| 見逃しを早く発見し、戻せるようにする（Anthropic） | マージ後の観測と、コード・設定・記録互換性を考慮した復旧方法を変更に添える。 | 検査を通した版と実際に動く版を照合する。マージと本番への適用を別の状態として扱う。 |
| 失敗を次の評価へ戻す（Anthropic） | 実際の不具合を回帰試験やレビュー評価に加える。正しい変更への誤指摘も記録する。 | 人間の作業時間・レビュー巡回数と、障害・revert の割合を併せて比較する。 |

用語・オントロジーは意味の共有、型・テストは振る舞いの検査、独立レビューは検査で拾い切れない問題の確認を支える。どれか 1 つで全体の安定性を証明するものではない。設計の理解を保つ責任と、既存の AI へのマージ委任は両立させる。記事の人間承認人数を新しい必須条件として写さない。

最初の実装範囲は、空テスト成功の除去、古い計測手順の同期、独立レビューと対象 commit の記録である。続いて一件の変更を、検査・レビュー・取り込み・適用後の確認まで通す。継続実行とメタハーネス的な改善は、その検証済みの工程へ接続する。

開発の安定性は PR・CI・障害の記録で測る。製品の改善は Trial・人間の観測・提出転帰で測る。評価対象、比較条件、採否基準を明示し、改善する側が結果に合わせて基準を緩めない。探索入力の比較と採否は DEVELOPMENT §5 に従い、人間の未観測を失敗や 0 点にしない。

## 適用しないものと未確認事項

[2026-10-15 の factory 調査](2026-10-15-software-factory-and-meta-harness.md)には同じ問いの履歴がある。当時の判定器・prompt・測定条件は現在の正本と異なるので、現状の証拠には使わない。
