# 対話型の連続提出セッション（2026-10-25）

## 問い

探索後の大量の Finding を、操作者が六つのスキルを個別に呼び出さず、ChatGPT または Claude との一つの会話で選別・検証・報告まで進められるか。

## 事実

- `origin/main` の `wbh-screen v4` は既に「明示除外だけを分け、曖昧な条件は検証へ」の方針である。公開ミラーに類例がないこと、時間窓、競合、通常構成が未確認という理由だけでは除外しない。
- 現行の六スキルは段階ごとの手順として存在する。利用者がそれらを個別に指名しなければならない、という実行上の必要はない。
- 現行 `wbh-review` は `incomplete` で `defer` を提案して終わり、未公開 Finding の具体的な説明を会話に出さない。`wbh-report v7` はブラウザ発火の観測を内部プレビューに留め、正式な Candidate には進めない。この二点は今回の対話型の実例と一致しない。
- SPEC 第 2 節は gVisor、Snapshot digest、Private Evidence、`runtime-confirmed` の意味、外部送信の承認を定める。SPEC と ADR 0038 は人間の手動再現を現行の正式な経路に置く。入口スキルの追加だけでこれらのゲートは変更できない。
- OpenAI と Anthropic の公式資料は、repo 内の `SKILL.md` を会話から明示または暗黙に呼び出す形を説明する。Codex は `.agents/skills`、Claude Code は `.claude/skills` を読む。同じ実体を symlink で共有できる。

## 所有者が選んだ運用

2026-10-25、所有者は「ハーネスが六段を無人で進める」形より、ChatGPT / Claude アプリから一つの提出作業スキルを起動し、複数の Finding を会話で順に処理する形を選んだ。原因、攻撃方法、被害者の行動、通常用途を人間が理解できることが目的である。

また、明確な programme 除外は AI が一括で選別し、対象に依存する前提（最初の数人に限る表示、短い時間窓、競合、管理者が特殊なフォームを作る構成など）は一律に棄却せず、人間との議論で扱うことを選んだ。大量の Finding は最初に安い一括選別を通し、その後は候補ごとに「前提を議論 → 必要なら Lab で確かめる → 判断に戻る」を繰り返す。全件の議論が終わるまで検証を止める必要はない。

## 入口スキルの流れ

1. 「提出作業を始めよう」「次の提出へ」または明示的なスキル指定で、同じ会話のセッションを開始・再開する。`review` の一覧、Private Evidence の既存判断、提出済み事実を読み直す。既に提出済み、提出しないと決めたもの、Programme Boundary の parked は次候補の一覧に出さない。
2. `wbh-screen v4` の明示除外だけを全候補へ安く当てる。残りは前提の軽さと未解決点を付けて並べる。AI の見立てを事実として扱わず、既知の却下例から新しい一律除外を即座に作らない。
3. 候補を一つ選び、プラグインの主用途、必要な設定、被害者が普段その画面に来るかを公式資料と固定 source で調べて短く示す。通常構成かどうかが難しい場合は、操作者との対話で決める。資料だけで決まらなければ対象版の gVisor Lab で小さく試し、その観測を持って議論に戻る。
4. 検証する候補は、攻撃前、攻撃者の入力、被害者の画面遷移、発火の各段を全画面画像とブラウザイベントで記録する。原因箇所の source、具体的な payload、攻撃者と被害者の操作、発火条件、通常用途との関係を同じ会話に短く説明する。動画は任意。未公開の材料と画像は Git 外の Private Evidence に保存する。
5. 操作者が画像と説明を見て「次へ進める／提出しない／追加検証」を選ぶ。環境や観測の失敗を脆弱性の否定にしない。実際の却下理由は個別に残し、複数の事例と公式規則で支えられる場合だけ `wbh-screen` の判定文を改訂する。
6. 提出候補は最新版、Wordfence scope、公開済み重複を確認し、短い英語の報告書とフォーム入力用 JSON を作って会話で見せる。拡張機能の JSON には内部状態を入れない。操作者が最終チェックと送信を行う。送信済みと言われたらチケット番号を要求せず、その事実だけ非公開で記録し、同じ会話から次の候補へ進む。

セッションは一つの Finding で終わらない。操作者が止める、候補が尽きる、または必須の判断を待つまで続ける。次の Finding では最新の queue を読み直し、同じものを二度出さない。

## スキルの配置と移行

入口を `wbh-submit` とし、`SKILL.md` の実体は `.agents/skills/wbh-submit/` に置く。Claude Code には `.claude/skills/wbh-submit` から同じ実体を読ませる。既存六スキルは当面内部の手順・参照として残す。人間はそれらを個別に呼び出す必要がない。利用実績がたまった時点で、重複する `wbh-review` と `wbh-destination` の統合・削除を判断する。

この最初の変更ではスキルの入口と会話上の進行だけを導入する。現行の正式な `review draft` / Submission Candidate のゲートを回避したり、ブラウザ発火を `runtime-confirmed` と呼び替えたりしない。画面・コードの人間査読を正式な提出 basis にする変更と、手動再現ゲートの変更は、SPEC・ADR 0038・Review API をそろえて別に実装する。

## 測ること

- 一回の会話で候補を何件処理し、うち何件が報告書・JSON・提出に進んだか。
- Finding 一件あたりの操作者の確認回数と経過時間。
- Lab の失敗が原因で「真偽不明」となった件数と、対話・追加観測で解消した件数。
- 通常構成や被害者の行動を理由に見送った件数と、後の実際の却下理由との一致。
