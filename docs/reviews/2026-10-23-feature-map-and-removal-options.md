## 1. そもそも何の道具か

この Harness は、AI が調べる対象を用意し、AI の実行を管理し、出てきた候補と確認結果を保存して、人間がレビューできる状態にする道具である。提出は人間が行う。

現在の main の通常設定では、無人ランナーは「候補の保存」まで。その後は、人がスキルを呼んで確認・レビュー・報告書作成を進める。各段を最初から最後まで自動で連続実行する仕組みではない。最後に本番で使われた checkout は main より古く、19:27 前後の観測ではランナーのプロセスが見つからなかった。

```mermaid
flowchart LR
  A[対象を選ぶ] --> B[ソースの版を固定]
  B --> C[AIの実行を管理]
  C --> D[候補を保存]
  D --> E[別の作業で確認]
  E --> F[人間向けに整理]
  F --> G[報告案と承認の記録]
  G --> H[人間が提出]
```

Harness が担うのは主に「準備・制限・観測・保存」。どこを読み、どう仮説を考え、どう解釈するかは AI とスキルの仕事である。Finding は「問題がありそうという候補」、Lead は「まだ材料が足りない手がかり」。どちらも確認済みとは限らない。

## 4. 実装ではなく、スキルがしていること

スキルは AI に渡す作業手順の文章。6 本あり、Harness の実装とは別に採否を決められる。

| スキル | 役割 | それだけではしないこと |
| --- | --- | --- |
| `wbh-screen` | 確認へ進める候補の材料を整理する | 判定器の「確認済み」は出さない |
| `wbh-verify` | 供給された Lab で確認作業を行う | 最終結果を自己申告だけでは確定しない |
| `wbh-dedupe` | 公開済みの情報との一致を調べる | 外部への提出はしない |
| `wbh-destination` | 提出先と、その理由を整理する | 送信はしない |
| `wbh-report` | 英語の報告案を作る | 人間の外部行動承認を代行しない |
| `wbh-review` | 人間が判断するための材料を読む | 所有者の最終判断を置き換えない |

現在は各スキルをつなぐ自動の一巡も、本番で文案保存から提出記録まで通った実績も確認できていない。したがって「6 本あるから、6 段すべて完成済み」とは説明できない。

## 5. 削除候補は 3 種類に分ける

### A. 機能を変えずに消せる可能性が高い残骸

| 候補 | 現状 | 消す範囲 |
| --- | --- | --- |
| `inspectOrphans` | 証拠ストアのメソッド。呼出は専用テストのみ | このメソッドと専用テスト。保存済みデータは触らない |
| `openReproductionPackage` | 旧レビュー向けの公開メソッドと reader。本体の呼出なし | 旧入口。現役の `openLabReconstruction` は別で残す |
| `Review.inspect` の余分な 4 項目 | 現在の呼出元は提出条件の評価だけを読む | 使われない返却項目と組立処理。メソッド全体ではない |
| deprecated alias | 旧定数名の定義・再 export だけ | 旧名。現役の定数と後片付け機能は変えない |
| 選定の薄い `select` メソッド | テストだけが呼び、本体は `decide` を使う | SPEC に契約が残るため、文書との整理を含めた候補 |

これは数か所の整理であり、44,374 行の大部分を削れるという話ではない。正確な削減行数は、残すテストと interface を決めた差分で測る。

### B. 廃止予定だが、移行条件が残る大きな旧機能

F14 の旧 Verifier・シナリオ選択・対象別 adapter 8 本・旧 campaign 内検証。今も到達する入口があるため、A と同じ扱いにはしない。既存の移行受け入れと、使えなくする入口を確認する。新しい機能を増やすより、まず既存の退役計画を完了できるかを見る候補である。

### C. 利用中でも、所有者の判断でやめられる機能

例えば、F01 自動選定、F04 provider 両対応、F05 無人継続運転、F06 再開、F16 群分け、F19 提出先調査補助、F21〜22 の文案・提出管理、F24 詳細集計は、今後の運用に要るかを判断できる。**「コードから呼ばれる」ことを、残す理由のすべてにはしない。** ただし採用済みの運用を変えるので、不要メソッドの削除と分けて扱う。

選び方は「残す／簡素化する／外の道具に任せる／やめる／保留」。F 番号で指定できる。機能全体をやめる場合は、その機能だけの設定・コード・テスト・説明も削除対象になる。不要機能を無効設定で温存することは前提にしない。

## 6. 機能の採否と別に、設計上直したい点

1. 人間レビューの入力検査が遅く、一部だけ記録してから失敗し得る。実害は未観測だが、順序の不整合がある。
2. 一覧・export・集計で、現在状態と過去記録の解釈が分散している。表示差を全部なくすのではなく、意味を揃えて説明する必要がある。
3. 読むだけの CLI も state の作成・書込み可能な接続を行う。監査と初期化の役割が混ざる。
4. 現行コード・旧本番版・手順文書の違いがあり、何が動いているかを理解しにくい。

削除前に機能の採否を決めれば、今後使わない部分までリファクタリングすることを避けられる。今回は説明資料の追加だけで、削除・リファクタリング・配備は行っていない。

探索時の attached Lab 自体まで廃止する別の判断を加える場合は、実装をさらに約 150〜220 行減らせる見込みだが、上の合計には含めていない。C の「現在使われる機能もやめる」は採否が未決定であり、削減量も未算定。現在の根拠だけで半分などの大幅削減を見込むことはできない。ソースコードは変更していない。

## 8. 残りの行数は必要で、適切に作られているのか

**その評価には至っていない。** 第 7 節は候補として特定できた旧処理の削減量であり、残る約 4 万行を必要十分と認定した数字ではない。「入口から呼べる」「実際に使われた」「所有者にとって必要」「実装が簡潔で正しい」は別々の問いである。初回棚卸しの「保持」は、利用実績のあるものを未使用扱いで即削除しないという分類であり、所有者による機能の採否を代わりに決めるものではない。

量の理由は説明できる。AI 実行まわりは 10,684 行、WordPress の Lab と検証は計 9,081 行、コマンドと各処理の接続は 7,998 行ある。単なる AI 呼出以外に、隔離、資格の仲介、固定したソースの取得、終了処理、保存、確認結果の表示まで自作している。これらの責務の存在は確認できるが、各責務の現在の行数が最小・妥当であることまでは示さない。

また、実利用のある部分にも設計上の問題がある。

- [レビュー操作の CLI](/home/dev/wordpress-bounty-harness/src/cli/index.ts:1063) は不正入力時の無書込みを意図するが、[Review 側の入力検査](/home/dev/wordpress-bounty-harness/src/review/index.ts:450) より先に一部の記録を行う。処理順序と検査の責務が分散している。
- [state の入口](/home/dev/wordpress-bounty-harness/src/cli/state.ts:19) と [Ledger の初期化](/home/dev/wordpress-bounty-harness/src/ledger/index.ts:771) は、閲覧だけの場合にも作成・書込み可能な接続を組み合わせる。保存が必要なことと、この接続方法が必要なことは別である。
- [イベント定義](/home/dev/wordpress-bounty-harness/src/ledger/index.ts:141) と [検索用の一覧](/home/dev/wordpress-bounty-harness/src/ledger/index.ts:665) が重複し、後者には 1 種の記載漏れがある。現在状態と履歴の解釈も Review・export・集計に分散している。

保存内容の digest 検査や矛盾する記録の拒否など、実質的な責務も存在するため、全体を水増しとも評価しない。現時点の判断は、**必要な基盤、運用上の選択機能、退役途中の処理、責務が混在した実装が同居している**というもの。小さな不要処理の削除だけでなく、所有者が必要とする機能を確定し、その機能の理解・変更に必要な箇所を減らすことに意味がある。リファクタリングによる純減行数は未算定であり、ファイル分割だけを改善とは数えない。
