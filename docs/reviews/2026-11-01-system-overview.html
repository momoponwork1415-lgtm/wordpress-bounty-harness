Bounty Harness 全体解説

WordPress plugin の脆弱性を見つけて Wordfence に報告し、報酬を得るための仕組み全体を、今日 main に入った状態で説明する。正本は docs/SPEC.md と docs/adr/ で、この文書は読むためのもの。

対象: 所有者状態: 探索は停止中、再開の準備は完了数字: 本番台帳 2026-11-01 20:40 JST 時点

1. 一言でいうと

この仕組みは 「WordPress.org の plugin を install 数の多い順に 1 つずつ取り、隔離環境の中で Codex のエージェント群にソースを読ませ、出てきた候補を人間が Lab で確かめて Wordfence に送る」 ための工場である。

設計の軸は 3 つの役割分担にある。

  • Harness（コード）は制御だけを持つ。何を対象にするか、ソースをどう固定するか、どこで動かすか、何分で止めるか、出てきたものをどう保存するか。判断はしない。
  • AI（目的文とスキル）が中身を持つ。どこを読むか、何を仮説にするか、Lab でどう再現するか、提出規則に照らしてどう読むか。
  • 人間（所有者）が確定と外部行動を持つ。Lab で自分の目で見た観測だけが「本物」の根拠になり、送信は人間が自分の手で行う。

過去 4 世代と 2026 年 10 月前半の失敗は、「探し方」を Harness のコードに入れて肥大させたことだった。いまの設計はその逆で、Harness から判断を削り、判断はプロンプトとスキルと人間に置く（AGENTS.md「Harness と AI の責務」、LESSONS 14）。

選定

問い: どの plugin のどの版を、どの順で見るか。

HARNESS
  • 母集団は WordPress.org の一覧。install 5,000 以上、180 日以内に更新、除外著者（Automattic、Yoast など 7 社）以外
  • install の多い順に 1 batch 10 件。同じ版は 1 回だけ。版が上がった slug は列に戻す（version-increased）
  • 操作者が名指しした候補も同じ列に入る
  • 公開履歴（Wordfence mirror）は選定では見ない
AI
  • 無し。報酬の有無は選定で判断しない
人間
  • 方針の数値（下限、鮮度、除外）を決める。対象ごとの承認は置かない（不変条件 6）
台帳: target-selected（理由 initial / version-increased）、selection-batch-bound、target-skipped。方針を変えて再起動すると最初の batch に selection-batch-discarded が 1 行出る。

Snapshot

問い: エージェントに何を渡すか。渡すものを後から同じ形で再現できるか。

HARNESS
  • 対象 plugin、WordPress 本体（最新安定版、ADR 0047）、実行 image に合う PHP ソース、依存 plugin を版と digest で固定
  • 依存は Requires Plugins ヘッダ、WooCommerce の版ヘッダ、方針の明示指定から決める。欠けたら黙って無視せず記録する
  • 渡すのはソース、trust 境界宣言、Programme Boundary、Lab、時点で切った公開履歴のカタログだけ（不変条件 1）。答え、PoC、ペイロードは渡さない
AI
  • 無し
人間
  • trust 境界宣言の文（contributor 以上と管理者が意図して与える権限は境界の内側）
台帳: snapshot-frozen。Finding と検証結果は同じ Snapshot digest のときだけ結び付ける（不変条件 5）。

探索

問い: 固定したソースの中に、未認証か Subscriber / Customer から届く対象範囲内の影響があるか。

HARNESS
  • gVisor（runsc）の使い捨て sandbox。外向き通信は認証ブローカー経由の provider API だけ（不変条件 2）
  • 対象 1 件につき 1 Trial。同時に生きる子は maxChildren（本番 8）まで。制限時間 120 分。5 対象並列
  • 目的文の末尾に ## Run parameters（時間・子の数）、## Prior research（同じ plugin の前の版の地図があれば場所と版）、出力契約（スキーマから生成）を Harness が付ける
  • sandbox にスキル file を置く。いま wbh-recon v2、wbh-tools v1、wbh-setup v1
  • 出力は全件保存し、契約 v4 で正規化する。棄却しない。止まった Root は同じ Snapshot で再開できる（ADR 0036）
AI（Codex）
  • 目的文 wp2shell-bounty-v21-wide（1 file、12 段落）。sink の種類ごとに専門エージェントを 1 体ずつ並列に走らせ、入口から sink へ、sink から入口へ辿る。脆弱性があるとは仮定しない
  • wbh-recon: 最初に plugin の地図（部分系、入口、認可の門、共有 helper、保存先、JS 境界）を recon-map.md に書く。子は親の会話を引き継がずに始める
  • wbh-tools: hook 登録と効果の呼び出しを一覧にして地図と突き合わせる
  • どこを読むか、何体使うか、いつ止めるかは Root が決める
人間
  • 目的文とスキルの文は owner-approved が付くまで渡らない（採否と付与は AI に委任、所有者の in-chat 決定を根拠にする）
  • 目的文の版は月 1 回まで、消す方向だけ（ADR 0045）
台帳: discovery-run-started / -finished（Root と子の両方。本番の累計 6,820 run）、discovery-concluded、candidate-normalized、finding-recorded、lead-recorded。地図と tsv は research として Git 外の attachment store に封じる。

出口

問い: 出てきた候補のうち、どれを検証列に流し、どれを人間の一覧に留めるか。

HARNESS
  • Programme Boundary 外の impact 10 種（CSRF、missing-authz、IDOR、reflected XSS、options-update など）は finding-parked。検証列に入れず review parked で見る
  • Lead は検証列に入れない。review leads で人間が全件見る
  • 同じ対象の別の版で同じ経路を見ていれば seen before: group … を表示する。判定はしない
AI
  • 無し。文言からの判定は置かない（「広く出して、落とすのはレビュー側」所有者決定 2026-10-26）
人間
  • park の 10 種の一覧を決めた（2026-10-17）。review restore で戻せる
台帳: finding-parked（累計 104）、finding-park-restored、candidate-held。

検証（6 段 + 1b）

問い: この Finding は本物か、提出して報酬が出る形か。

HARNESS
  • Lab の供給: gVisor の中の WordPress + MySQL。基線 v3 = 素の WordPress に管理ホスティング（Sakura / Xserver 級）の既定設定を重ねる。Wordfence が受け付ける入口は塞がない
  • 外部サービス（Facebook など）の経路は、宛先ごとの中継 container を立てて前提作りのときだけ通し、setup-done で閉じて届かないことを確かめる（ADR 0046）。公開入口の開閉と API キー入力は人間
  • HTTP 捕捉と Lab browser の記録。人間の観測（review observe、review decide --reproduced）の記録
  • 判定器も canary も持たない（ADR 0040）
AI（スキル）
  • 段 1 wbh-screen: 規則の写しで明白に除外されるか
  • 段 1b wbh-source-check: 固定ソースだけで「低権限が入力を握れるか」「既定かもっともらしい設定で sink に届くか」
  • 段 2: 同じ Snapshot の同じ経路を群にし、代表から見る
  • 段 3 wbh-verify v12: Lab の通常機能で前提を作り、setup-done 後は攻撃者の位置だけで route を実行して 6 file を書く。判定はしない
  • 段 4 wbh-dedupe、段 5 wbh-destination、段 6 wbh-report（英語報告書と form JSON）
  • 段 1・1b・4 の中間判断は --by ai で記録し、人間が覆せる
人間
  • Lab で自分の目で見た観測だけが確定の根拠。AI が会話の中で所有者の言葉を受けて --by yuto で記録する。人間はコマンドを打たない
  • 検証の失敗（環境、手順、観測不足）は incomplete。棄却にはしない（不変条件 4）
台帳: lab-provisioned（基線と egress の宛先を含む）、verification-finished、review-decided（理由コードで段の印を打つ）、human-effort-recorded、manual-observation-lab-ready。ペイロード、HTTP 記録、画面画像は Git 外の Private Evidence（不変条件 8）。

提出と転帰

問い: 送るか、どこへ送るか、結果をどこへ戻すか。

HARNESS
  • 送信はしない（不変条件 7）。review submitted で提出を、review outcome で転帰（paid / CVE のみ / 重複 / 却下）を台帳に記録する
AI
  • wbh-submit の会話で、選別 → 検証 → 説明 → 報告書までを順に進める
  • 転帰は wbh-screen の規則と Lab の基線に戻す。探索の目的文には戻さない（契約 v5 で出力が 76 → 8 に減った教訓）
人間
  • 自分の拡張機能で Wordfence のフォームに入れて送る。提出前のレビューと外部行動の承認が人間の 2 つの判断点（不変条件 6）
台帳: submission-recorded-externally（18 Finding）、submission-outcome-recorded（7 件: 範囲外 4、受理 1、却下 2）。

3. 守っているもの

設計・実装・レビューのすべてで見る不変条件 8 つ（SPEC 第 2 節）を、短く言い直す。

  1. エージェントに渡すのは固定ソースと境界の宣言と時点で切ったカタログだけ。答えや PoC は渡さない。
  2. 対象は gVisor の中でだけ動かす。外向きはブローカー経由の provider API だけ。
  3. Harness は判定器を持たない。確定は人間の review observe の match と review decide --reproduced match だけ。
  4. 検証の失敗は incomplete。棄却にも否定にもしない。
  5. Finding と検証の Snapshot digest が同じときだけ判定する。
  6. 人間の判断点は提出前レビューと外部行動の承認の 2 つ。対象選定の承認は置かない。
  7. 外部送信は、正確な候補と文案の版と送信先に結び付いた承認があるときだけ。Harness は送らない。
  8. 台帳は追記専用で digest 参照だけ。中身は Git 外の Private Evidence。

加えて ADR 0045 の「凍結 5」がある。人間の観測だけが確定、Harness は制御だけ、台帳は追記専用、分母は 1 つ（Codex 1 時間あたりの Lab 発火数と Wordfence の結果）、目的文の変更は月 1 回で消す方向だけ。今日の v20 → v21 は「消すだけ」なので範囲内である。

7. 再開後に見るもの

  • 分母は 1 つ: Codex 1 時間あたりの Lab 発火数と、Wordfence の結果。Finding と Lead の数は観測として読むが採否の基準にしない。
  • Trial の健全性: discovery-run-started の prompt 版が v21-wide か、Root ごとの子の数、wall、読んだ file 数、トークン。失敗は incomplete の理由コードで見る（docs/agents/production-monitoring.md）。
  • prior research の効き: configuration.priorResearch が passed になった Trial と none の Trial で、Finding の数と重複の表示を比べる（ADR 0048 は「数字を見てから」スキルに足すと決めている）。
  • 検証列: 新しい Finding は段 1 → 1b → 群 → Lab の順に進める。Lab は plugin 単位でまとめ、人間の観測が付いたものだけ段 4 以降へ。
