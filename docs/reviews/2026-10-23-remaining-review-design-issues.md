# リファクタリング後に残るレビュー・保存・CLIの設計課題

2026-10-23。main `5e4de0e` に今回のレビュー・保存リファクタリングを合わせたコードの読み取り評価。対象はReview、Ledger、PrivateArtifactStore、CLIの保存・閲覧操作。実際の障害発生や利用頻度を調べた報告ではない。探索・検証実行方式の追加評価は含めない。

品質ゲートが通ることと、設計上の課題が無いことは別である。以下は今回の7項目で解決しきっていないもの。追加修正はこの評価を根拠に選ぶ。

## 優先順位

### 1. 判断対象の一致と、追記順の意味を揃える — Strong

根拠: `src/review/index.ts:626` は、過去の `incomplete` / `contradicted` への判断を制限するが、過去のconfirmed参照は許可する。`src/review/decision-history.ts:38` は現在の判断を追記順だけで決める。

古い検証記録を指定して後から判断を書くと、新しい検証記録のqueueにもその判断が有効と見える条件がある。今回の変更が保存・表示の従来の意味を維持したため、残っている既存課題である。通常のCLIは現在のqueue項目を選ぶので、主にReviewのinterfaceを直接使う場合の整合性が問題になる。

改善方向: Review moduleで「現在有効」の定義に対象参照とdigestの一致を含めるか、過去への判断は履歴としてのみ扱うことを明示する。queueの導出と記録の検査を同じ意味へ揃えるとlocalityが改善する。履歴を読むexportの意味は保つ。

mainの `#finalReviewGate` / `#isCurrentVerification` は、提出承認時に最新参照とdigestを別途照合する。この指摘はqueue表示の整合性であり、外部行動の承認を通過できる問題とは扱わない。

### 2. 一件の閲覧で無関係な保存物を読まない — Strong

根拠: `src/review/index.ts:1340` と `:1346` は全件のassessment / draftを読んでから対象を絞る。`:1472` と `:1490` の読取りは全キャンペーンに及び、`:1465` の必須artifactの欠落は例外になる。

そのため、ある過去キャンペーンのartifactが失われると、無関係な候補の閲覧・文案操作まで失敗し得る。記録が増えるほど読取り量も増えるが、性能の実測はまだしていない。

改善方向: Ledgerのmetadataで対象を絞ってから、必要なPrivate Evidenceだけを読む。対象自身の必須記録が欠けている場合は引き続き明示的に失敗させる。Reviewと保存adapterのseamで読取範囲を閉じれば、複数の呼出先にleverageがある。新たなDBや汎用moduleを増やす必要はない。

### 3. 人間の記録操作を安全にやり直せるようにする — Worth exploring

根拠: `src/review/index.ts:503` は複数イベントとPrivate Evidenceを個別に保存する。人間イベントのidentityは `:1256` / `:1285` で毎回生成する。

今回、不正入力による部分保存は防いだ。しかし保存途中のI/O障害では途中まで残り得る。同じ入力でやり直すと、所要時間などが重複する条件がある。CLIの `review submitted`（`src/cli/index.ts:1473`）と `review outcome`（`:1518`）も、主記録の後に任意工数を入力・保存するため、工数側の失敗で全体が失敗表示になる余地がある。

改善方向: 人間操作の識別子・再実行時の扱い・主記録と任意工数の成功状態を先に決める。そのうえで、関連台帳イベントの一括保存とartifactの保存手順をReview moduleの内部に閉じる。呼出側に復旧順序を覚えさせないことでinterfaceのdepthが増す。SQLiteとファイルが自動的に同一トランザクションになるわけではなく、障害時の扱いを決める作業が必要である。

### 4. コマンドに渡す保存機能を必要な範囲にする — Worth exploring

根拠: `src/cli/index.ts:1877` は全コマンドでLedgerを開く。`history status` の実装（`src/cli/wordpress.ts:1107`）は時計だけを使う。`src/cli/state.ts:8` の型には、readOnlyのときも書込み可能なPrivateArtifactStoreとID生成器がある。

現在の閲覧コマンドが保存している証拠は無く、DBのreadOnly接続と非書込みテストもある。一方、時計だけで済む確認までDBを必要とし、型から読み取り専用の意図を確かめづらい点は今回残した制約である。

改善方向: 状態不要・読取・書込の3種類を、実際のコマンドの必要に合わせる。読取側にはArtifactReaderなど必要なinterfaceだけを渡す。操作方式をCLIから変える話とは独立して改善できる。

### 5. CLIの検査結果を、そのまま実行入力にする — Worth exploring

根拠: `src/cli/index.ts:1136` からのvalidateで確認したdecision・reproduction・duplicate・minutesを、`:1170` からのhandlerで再び変換する。prepareが保持しているのは生のFlagValuesである。

現時点のテストは通るが、制約変更時に2か所を同期する保守負担がある。これは今回の入力検査の移動後にも残った整理余地である。

改善方向: CLI adapterのprepareから正規化済みの入力を渡す。Reviewの業務上の検査は保持し、CLI固有の字句解析・変換を一度にまとめる。外部CLIライブラリを入れる必要性は、この問題だけからは導けない。

## 次に着手するなら

まず1と2を小さく分けて扱う。利用者に見える整合性と、無関係な記録への依存を改善でき、合成記録で受入条件を作れる。3は復旧の意味を先に決める。4と5はCLIの追加変更が必要になった時に合わせる。

Knipの未参照exportも残るが、参照数だけで機能の不要を断定しない。大きなファイルを分割すること自体も目的にしない。deletion testでは、責任を消せるか、別の呼出側へ移すだけかを区別する。
