# Anthropic・Google Mantis・Cloudflare の公開ハーネス調査（2026-10-13）

問い: 公開された防御側の脆弱性探索ハーネスから、現在の WordPress バグバウンティ Harness に役立つ事実は何か。

方法: 各社の記事と所有する GitHub リポジトリの一次資料を確認した。GitHub の参照先は今回読んだ commit に固定した。コードを実行して性能や隔離を再現した調査ではない。公開日と source の最終 commit 日は区別する。現行仕様との照合先は [SPEC](../../SPEC.md)、[DEVELOPMENT](../../DEVELOPMENT.md)、[LESSONS](../../LESSONS.md)。

## 要点

- **共通する強い根拠は探索の複雑化より、候補を失わない記録、独立した再検証、実行環境の強制、証拠付きの人間への受け渡しにある。** Anthropic は発見と検証を別の役割に分け、Cloudflare は source に結び付いた保留候補を残し、Mantis は再現失敗を即座に偽陽性と見なさない。各社の「verified」には異なる判定基準があるため、当地の `runtime-confirmed` と同義にはしない。[Anthropic best practices](https://github.com/anthropics/defending-code-reference-harness/blob/d3bea6b5793b5f3d59a75ebe69a58efa88383145/docs/best-practices.md)、[Mantis README](https://github.com/google/mantis/blob/2b3bbdcbb8d259d1777b89dcfa3c8e87615ccc80/README.md)、[Cloudflare skill](https://github.com/cloudflare/security-audit-skill/blob/c1c8a8c1471069fb0e188eeaff69b8e8db6564a8/skills/security-audit/SKILL.md)。
- **3件とも、このリポジトリの探索 prompt や単一協調 Trial を今すぐ変更する根拠にはならない。** Anthropic の公開自動 pipeline は C/C++ の ASAN crash、Mantis は多段の汎用設計、Cloudflare は単一 repo の防御側監査が中心。WordPress の報奨対象候補について、同じ予算と同じ判定器で現行方式より良いという比較結果は見つからなかった。[Anthropic pipeline](https://github.com/anthropics/defending-code-reference-harness/blob/d3bea6b5793b5f3d59a75ebe69a58efa88383145/docs/pipeline.md)、[Mantis architecture](https://github.com/google/mantis/blob/2b3bbdcbb8d259d1777b89dcfa3c8e87615ccc80/README_AGENTS.md)、[Cloudflare README](https://github.com/cloudflare/security-audit-skill/blob/c1c8a8c1471069fb0e188eeaff69b8e8db6564a8/README.md)。

## この Harness での読み方

1. **既存 Step 1 に直結する観測点:** `review export` が scope 内 Finding を `incomplete` のままでも source/snapshot、実行時証拠参照、正確な不足事実とともに人間へ届けるか。`candidate-held` は Finding とは別に記録されるため、同じ review 対象だと推定しない。これは Anthropic の独立検証、Mantis の再現失敗時の留保、Cloudflare の `needs_validation` と近い問題に対する現在の設計の実測である。[DEVELOPMENT 第2節](../../DEVELOPMENT.md)、[SPEC 第6・7節](../../SPEC.md)、[ADR 0018](../../adr/0018-hold-and-normalize-discovery-candidates.md)。
2. **隔離の参照:** 各公開物は設定文だけでなく agent と対象コードの実行場所を区別する。現行の `runsc`・provider broker・fallback 禁止を preflight で観測する材料になる。Mantis の複数 sandbox backend や Anthropic の明示 bypass を取り込む提案ではない。[SPEC 第2節](../../SPEC.md)、[Anthropic sandbox](https://github.com/anthropics/defending-code-reference-harness/blob/d3bea6b5793b5f3d59a75ebe69a58efa88383145/docs/agent-sandbox.md)、[Mantis tool boundary](https://github.com/google/mantis/blob/2b3bbdcbb8d259d1777b89dcfa3c8e87615ccc80/reference/README.md)。
3. **後で比較する仮説:** Cloudflare の「single run は反復の累積発見の約半分」という数値と、Anthropic の再走査推奨は、その対象・運用の経験である。この Harness の対象ごと1回を否定する測定ではない。現行 Trial の wall、source 読取、候補、費用、提出転帰に不足が出た時だけ同条件の A/B を考える。[Cloudflare 記事](https://blog.cloudflare.com/build-your-own-vulnerability-harness/)、[Anthropic best practices](https://github.com/anthropics/defending-code-reference-harness/blob/d3bea6b5793b5f3d59a75ebe69a58efa88383145/docs/best-practices.md)、[SPEC 第10節](../../SPEC.md)。
4. **coverage の意味は分ける:** Cloudflare の coverage ledger は監査範囲・未処理・保留を明示するためのもので、quick/scoped run を部分的な範囲と表示する。この Harness の入口索引は所在のカタログで、全入口の処理を Trial の正常終了条件にしない。coverage の可視化という点だけが参考になる。[Cloudflare skill](https://github.com/cloudflare/security-audit-skill/blob/c1c8a8c1471069fb0e188eeaff69b8e8db6564a8/skills/security-audit/SKILL.md)、[SPEC 第6節](../../SPEC.md)。
5. **運用上の失敗を正常0件と混ぜない:** Cloudflare は provider の一時エラーが `200 OK` の本文として返り、空の正常 run に見えた経験を明記する。Anthropic の参照実装は rate limit 後の再開と、先に提出された成果の救済を持つ。この repo は自動 retry しない決定なので再開方式を移植せず、quota・broker・schema の失敗を理由付き `incomplete` にできたかを Step 1 の台帳で見る。[Cloudflare 記事](https://blog.cloudflare.com/build-your-own-vulnerability-harness/)、[Anthropic pipeline](https://github.com/anthropics/defending-code-reference-harness/blob/d3bea6b5793b5f3d59a75ebe69a58efa88383145/docs/pipeline.md)、[SPEC 第6節](../../SPEC.md)。

## 補助的な新着一次資料

- Anthropic は [Cyber Verification Program の拡張（2026-10-06）](https://www.anthropic.com/news/cyber-verification-program)を発表し、Glasswing をその枠組みへ統合した。これはモデルの利用資格・safeguard の情報であり、当地の pipeline がそのモデルを利用可能だという証拠でも、切替えの効果測定でもない。10-08 の [Cyber Mission](https://www.anthropic.com/news/anthropic-cyber-mission) は open-source project 向け定期 scan を発表したが、公開記事だけでは WordPress バグバウンティ用の検証契約や費用の比較はできない。
- 同日公開の [OSS Scanner の説明](https://www.anthropic.com/research/launching-opt-in-vuln-finding-service-for-open-source)と[FAQ](https://red.anthropic.com/oss-scanner/)によると、登録した保守者には人間が未確認の報告を送る。これは**保守者の opt-in** と受け手側の処理能力が前提で、通常の外部バグバウンティ提出の先例にはならない。Anthropic は高・重大97件を人間が確認した初期評価で85件が同社の CVD 基準を満たしたと報告するが、選別済み標本の結果であり、この Harness の候補品質には換算できない。報告 bundle に再現器、説明、可能なら修正案を含める点は `review export` の材料の比較に使える。
- [Cloudflare の 2026-06-18 記事](https://blog.cloudflare.com/build-your-own-vulnerability-harness/)は、公開 skill は単一 repo の出発点で、実運用の多 repo harness 自体は未公開と説明する。記事の fleet-wide 数字を GitHub skill の実測値として扱わない。

## 未確認・限界

- GitHub の creation/push 日は GitHub API で 2026-10-13 に確認した repository metadata で、リリース日ではない。`updated_at` はスター等でも動くため source 更新日として使わなかった。
- Mantis の文書にある構造的な gate と自動 downgrade の関係は設定・実行経路ごとに違う。今回は source の読解のみで、全構成の強制力を動的に確かめていない。
- 3件の成果数字は各社の自己報告。対象、モデル、予算、判定器を固定した当地の比較ではなく、未知の WordPress 脆弱性発見率や報奨額は推定できない。
