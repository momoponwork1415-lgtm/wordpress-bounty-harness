1この Harness が何をするか、何をしないか

目的は 1 つ。WordPress プラグインの未知の脆弱性を AI に探させ、実行時検証を通ったものだけを人間が Wordfence（第 2 候補として Patchstack）へ提出して報奨を得ること。収益は「月に回せる対象数 × 当たり率 × in-scope 率 × 平均報奨 − 月費用（約 $700）」で考える。費用は ChatGPT Pro の購読（Codex CLI 認証）で固定され、Harness は金額ではなく quota / rate limit を見る。

docs/SPEC.md §1、§14

やること

  • 対象を方針どおりに機械選定し、source を digest で固定し、gVisor の使い捨て Lab を立て、Root＋最大 3 子の協調 Trial を対象ごとに 1 回回す。
  • 出てきた候補を正規化して受理・保留・park に分け、受理した Finding を独立 Verifier と Harness 所有の判定器で確かめる。
  • 全段階を追記専用の台帳に残し、人間が読む材料（review export）を 1 件 1 本の JSON で出す。

やらないこと

  • 外部送信（報告、ベンダー連絡、公開）。Harness 自身は送らない。
  • 対象選定の人間承認、未検証候補の人間による採否。
  • 探索 agent への PoC・payload・再現手順・評価対象の答えの提供。
  • ホストでの対象コード実行、弱い隔離への暗黙の切り替え。
  • payload・HTTP 記録・画面画像・未公開の発見を Git に置くこと。

docs/SPEC.md §2、docs/OPERATIONS.md §7

人間の判断点は 2 つだけHUMAN
(1) 提出前のレビュー、(2) 外部行動の承認。権限・対象範囲の拡張も人間の明示承認を要する。それ以外（選定、固定、Lab、探索、検証、台帳）は無人で回る。docs/SPEC.md §2 不変条件 6；docs/adr/0006

28 つの不変条件を、所有者の言葉で

設計・実装・レビューのすべてで守る 8 項目。各項目に「なぜそうしたか」を過去の教訓と ADR から添えた。

  1. 探索 agent に渡すのは、固定 source、trust 境界宣言、Programme Boundary、Lab、時点で切った公開履歴のカタログだけ。答え・PoC・payload・再現手順は渡さない。

    なぜ: 評価が汚染されると「見つけた」が「なぞった」と区別できない。旧 ADR 0001 は履歴を全面禁止したが、公開日で時点を切れば汚染は防げ、本番では「修正の回避」「同じパターンの別関数」を狙える。

    docs/adr/0012；docs/adr/0027

  2. 対象を動かすのは gVisor（runsc）の使い捨て環境の中だけ。ホストでは動かさない。外向きは認証ブローカー経由の provider API だけ。

    なぜ: 探索 agent に Lab 内実行を許すと精度が上がる（公開事例と一致）が、その代償として Lab 外への到達・永続化・外向き通信を機械的に塞ぐ必要がある。API キーや OAuth token は agent のコンテナに入れず、run ごとの broker が model・件数・大きさ・期限を強制して中継する。Codex CLI 内側の sandbox は無効化し、外側の runsc と broker を必須にすると 2026-10-08 に決めた。

    docs/adr/0003；docs/adr/0009；docs/SPEC.md §14

  3. runtime-confirmed を出せるのは Harness 所有の決定論的判定器だけ。証明は nonce 付き canary の回収に限る。

    なぜ: LLM の合議が存在しない脆弱性を全員一致で支持した事例があり、同じ Verifier が成立した書き込みを「反証」として書いた例も本リポで観測した。agent の自己申告、リバースシェル、永続化、ホストアクセスは証明に数えない。

    docs/adr/0004；docs/adr/0031「採らなかった選択肢」

  4. 検証の失敗（環境、手順、観測、証拠の不足）は incomplete。contradicted にも棄却にもしない。

    なぜ: 偽陰性は偽陽性より高くつく（本物を落とすと報奨を失う）。初期実装では自由文の反証メモの存在だけで contradicted が出て人間の列から消えていた。incomplete は理由コードと次の手を持ち、別列で必ず表示する。

    docs/adr/0002；docs/LESSONS.md 10；docs/reviews/2026-10-11-thorough-design-review.md H1

  5. 判定は Finding と検証結果が同じ Target Snapshot digest を持つときだけ。不一致は incomplete。

    なぜ: 版がずれた Lab で確認しても、どの版の主張を確認したのか言えない。最新版での再検証は新しい Snapshot に結び付けた別 Finding として記録し、旧 Finding への由来だけを参照する。

    docs/adr/0005；docs/SPEC.md §2 不変条件 5

  6. 人間の判断点は「提出前のレビュー」と「外部行動の承認」の 2 つ。対象選定の承認と未検証候補の採否は置かない。

    なぜ: 前の harness の問題は「対象選定に人間が入る」「結果確認に人間が入る」の 2 点だった。前者は自動選定で解き、後者は人間を無くすのではなく読む件数を Harness が絞ることで解く。人間に見えない成果は無いのと同じ（再現済み 30 件と候補 12 件が放置された世代がある）。

    docs/DEVELOPMENT.md §1；docs/adr/0006；docs/LESSONS.md 5

  7. 外部送信は、正確な Submission Candidate・文案の版・送信先に結び付いた承認があるときだけ。Harness 自身は送らない。

    なぜ: 文案は skill が書くが、その digest と承認の結び付きは Harness が台帳に記録する。「この版のこの文案を、この送信先へ」が残っていなければ、後で何を出したか辿れない。送信は人間が Wordfence の画面で行い、submitted と outcome で記録する。

    docs/SPEC.md §2 不変条件 7；docs/adr/0031；docs/OPERATIONS.md §3

  8. 台帳は追記専用で、持つのは digest 参照だけ。payload、HTTP 記録、画面画像、実行ログ、認証情報、未公開の発見は Git 外の Private Evidence に置く。

    なぜ: リポジトリは公開で、未公開の発見や payload が Git に入れば取り返しがつかない。CI の private-guard が path・大きさ・内容（canary token、HTTP 捕捉、鍵、cookie）を走査する。追記専用なので、既存 event を書き換える代わりに新しい event を足す。

    docs/adr/0005；docs/DESIGN-DIAGRAMS.md §4；docs/DEVELOPMENT.md §5

31 つの Trial の一生

campaign 1 周は「選定 → 固定 → Lab → 探索 → 正規化 → 検証 → 台帳 → review」。紫の点が人間、黄の点が設計中の段。下の図は現行の主経路（ADR 0029）で、2026-10-18 に merge された「探索用 Lab 任意」「verify next」を含む。

  1. ① selection — 対象を機械的に選ぶ
    Harness（selection.json が正本）
    母集団
    WordPress.org の人気順 10 頁と 8 タグ族（forms、contact-form、membership、page-builder、elementor-addons、multilingual、backup、booking）各 1 頁。
    条件
    アクティブインストール 100,000 以上 1,000,000 未満、更新 365 日以内。除外作者 7 社（Automattic、Facebook、Google、MailPoet、SiteGround、WooCommerce、Yoast）。
    順位
    log10(1+installs)×10 ＋ 鮮度×5。公開履歴の件数は plugin 単位の順位・除外に使わない（ADR 0030）。
    再訪
    revisitPolicy: never。Trial として数えた slug は版が上がっても戻らない。旧世代の既往は Git 外 legacy-history.json で除外。
    出力
    1 batch 3〜5 対象。target-selected と selection-batch-bound を台帳へ。承認は不要。

    src/profiles/wordpress/policy/selection.json；docs/adr/0032 Q3〜Q9、2026-10-16 節；docs/OPERATIONS.md §5「対象の自動選定」。注: ADR 0032 は除外作者 5 社と書くが、selection.json は #304/#306 で 7 社になっている。

  2. ② Target Snapshot — source を digest で固定する
    snapshot モジュール ＋ profile の acquisition

    plugin の zip と WordPress core（campaign.json では 7.1.3、開発セットの image は 6.8.3）を canonical manifest の digest で固定する。archive の不正 path・symlink・size 超過は拒否。以後の全 event はこの digest を持ち、探索と Verifier は /workspace の read-only mount で同じ版を読む。

    docs/SPEC.md §4；src/profiles/wordpress/policy/campaign.json；docs/evaluation/README.md

  3. ③ Lab — 使い捨ての WordPress + MySQL
    lab モジュール ＋ profile の lab（gVisor）

    runsc 上に WordPress、MySQL、canary、HTTP 捕捉 proxy の container を立てる。agent に渡す認証情報は未認証・subscriber・customer だけで、contributor 以上と管理者は渡さない。設定は既定のまま、「通常機能 scenario」（版と digest 付き、plugin 非依存を優先）で無害な初期データだけ入れる。DB は provision 時点の table だけ読める read-only account。

    2026-10-18 から探索用 Lab は任意（discovery.lab: "attached" | "none"）。none なら探索は source だけで走り、Finding は後で verify next が Finding 単位の Lab を立てて検証する。

    docs/SPEC.md §8b；docs/adr/0020、0026；docs/adr/0029（2026-10-18 追記）；docs/OPERATIONS.md「探索だけ回し、検証を 1 件ずつ回す」（PR #321）

  4. ④ discovery — Root＋最大 3 子の協調 Trial を 1 回
    Codex CLI（gpt-6-sol 系）を gVisor sandbox で、broker 経由
    渡すもの
    目的 prompt（既定 wp2shell-bounty-v5、digest 固定）、trust 境界宣言、Programme Boundary 文（wordfence-2026-10-17 版）、固定 source、Harness 生成の入口索引（AJAX action / REST route / shortcode / request-hook の所在カタログ。経路や分担は指示しない）、Harness 生成の出力契約の節（Finding / Lead の schema から生成。ADR 0019）、任意の Lab。公開履歴は渡さない運用。
    構成
    Root が分担と仮説を決め、子は最大 3。子の Finding と Lead は Root の最終 JSON と独立に保存する（Root が wall で止まっても子の成果は残る）。
    停止
    Root の最終報告で正常終了。最低時間は置かない。wall 上限は campaign.json で 60 分（v6 計測用 config は 120 分）。wall・provider 上限・broker 上限・schema 失敗は理由付き incomplete で、候補 0 件の正常完了に数えない。
    深さの記録
    Root は入口索引の各 id を observed / blocked で報告し、Harness が検証する。未訪問が coverage.maxUnvisitedRatio（既定 0.2）を超えると incomplete(depth)（PR #320）。
    Trial に数えない
    Root が source を 1 件も読まず、子を起動せず、broker 転送が 1 以下で終わった run。その対象は次の選定に戻る。
    broker 上限
    Root＋3 で provider 要求 1,600 件、要求本文 8 MiB。超過は incomplete(policy)。

    docs/adr/0029；docs/SPEC.md §6；docs/adr/0019；src/profiles/wordpress/policy/campaign.json；docs/OPERATIONS.md §2。注: AGENTS.md は既定を wp2shell-bounty-v3 と書くが、SPEC と campaign.json は v5。

  5. ⑤ 候補の正規化 — 受理 / 保留 / park
    Harness（profile の normalize-candidate、programme-impacts）

    Root と子の最終 JSON から抜いた候補は、まず生のまま Private Evidence に保存する。次に構文だけの正規化（文字列配列の結合、sourceTrace の構造化、@wordpress/ 接頭辞）を通し、schema を通れば Finding か Lead として受理する。通らなければ candidate-held（分類と issue path だけ台帳に残し、後で再受理できる）。候補を出力境界で棄却しない。

    受理した Finding のうち impact が Programme Boundary の外にあるものは finding-parked として台帳と Private Evidence に残し、検証 queue・review queue・funnel の raw に入れない。park される分類は 10: other、csrf-to-write、missing-authz、idor、reflected-xss、sensitive-object-access、content-deletion、options-update、privesc-to-contributor+、auth-bypass-non-admin。残る分類は RCE / PHP file write、PHP に届く任意ファイル read / delete、管理者への privesc / auth-bypass、account takeover、SQLi、stored XSS、任意ファイル read / delete / download、LFI / RFI。

    docs/adr/0018；docs/adr/0032（2026-10-17 節）；src/profiles/wordpress/discovery/programme-impacts.ts。注: AGENTS.md は content-deletion を park から除外すると書くが、2026-10-17 の所有者決定でコードは park する。

  6. ⑥ verification — Verifier と判定器
    Verifier（別コンテナ、verifier-v7）→ Harness 判定器（judges.ts）

    Verifier は探索の会話を持たない新しいコンテナで、Finding・固定 source・Lab endpoint・低権限 account・RO DB・Lab Setup と、impact に応じて Lab が発行した canary を受け取る。役割は手順の整備と「発火したか」の確認（2026-10-13 に「反証」から向きを変えた）。再探索はしない。HTTP は Lab 内の Harness 所有 reverse proxy に向け、request / response は Harness が捕捉する。被害者側の操作は Harness 所有の観測器が型付き手順で行い、Verifier にブラウザや管理者セッションは渡さない。

    判定器は分類ごとに成功条件が固定されている。RCE / PHP file write は Execution Canary（nonce）の実行痕跡、SQLi は canary 行の読み書き、任意ファイル read は Lab が置いた canary file の内容、管理者への昇格 / ATO は canary ユーザーとロール別正常操作との差分、stored XSS は低権限主体が置いた nonce 付き値が被害者ロールの画面で headless browser 上で実行され canary 受信先へ届くこと。timing 差、文字列の反射、alert の有無、自己申告は不採用。

    結果
    runtime-confirmed / contradicted / incomplete。
    incomplete の理由
    provision、precondition、recipe、observation、evidence、cleanup、digest-mismatch、no-judge（判定器が無い分類）。探索側には depth。
    自動再試行
    recipe 2 回、observation 2 回、provision 1 回、precondition は scenario ID が変わったときだけ、provider 上限 1 回。attempt 番号と前の verificationId を台帳に残す。
    前提の分類
    Finding の configurationPrecondition を Harness の決定論的規則で default / common-usage / admin-configuration / unknown に分ける。admin-configuration は finding-parked(admin-configuration-precondition)、common-usage は対応 scenario への有界再検証、unknown は incomplete(precondition) として review queue に残す（PR #316）。

    docs/SPEC.md §7；docs/adr/0004、0021、0022、0026；docs/adr/0032（Q14、ADR 0022 への修正）；src/profiles/wordpress/verification/precondition-class.ts

  7. ⑦ ledger と Private Evidence
    ledger モジュール（SQLite、追記専用）

    全モジュールが型付き event を 1 つの台帳に追記する。例: target-selected、selection-batch-bound、snapshot-frozen、lab-provisioned、discovery-run-started / finished、discovery-concluded、candidate-held、finding-recorded、finding-parked、lead-recorded、verification-finished、review-decided、scope-assessed、draft-saved、external-action-authorized、submission-outcome、campaign-stopped、target-skipped。全 event が snapshot digest と campaign id を持ち、本文（候補、HTTP、payload、画面、rollout）は content-addressed の Private Evidence にあって台帳は digest だけを持つ。funnel・usage・stops・runtime は台帳から読み取り専用で導く。

    docs/SPEC.md §9；docs/adr/0005、0023；docs/DESIGN-DIAGRAMS.md §2

  8. ⑧ review queue → Submission Candidate HUMAN
    所有者 ＋ skill 3 本

    Programme Boundary 内の Finding は判定器の結果に関係なく全件 review queue に出る（#185、ADR 0031）。runtime-confirmed には再現パッケージ（手動手順、Python 最小スクリプト、Lab 再構築情報、判定器の証拠）が付き、incomplete には理由と次の手が付く。contradicted は件数だけ。

    所有者は review export で 1 件分の JSON を出し、wbh-review（要約と accept / reject / defer の提案）、wbh-dedupe（mirror と Patchstack / WPScan 照合、3 値）を使い、最新版で review reverify、review scope、必要なら lab up --for-review で手で再現して review reproduced、review decide。accept なら wbh-report が英語下書きを Private Evidence に書き review draft で digest を記録。review authorize --to wordfence（判断点 2）の後、所有者が自分で送信し submitted、後日 outcome（triaged / resolved / duplicate / informative / N/A / rejected、報奨額）。

    docs/OPERATIONS.md §3；docs/adr/0031；docs/SPEC.md §8

台帳から見える funnel
協調 Trial の実行と完了 → 最終 JSON 到達 → 受理 / 保留 → verifier 通過 → confirmed / contradicted / incomplete → reviewed → in-scope → submitted → outcome。campaign 別・arm 別・分類別。索引あり／なし、旧段付き Trial、v5／v6 は同じ分母に混ぜない。docs/SPEC.md §10；docs/adr/0023、0029

4データはどこにあるか

もの 場所 Git 中身
台帳 --state <dir> の SQLite。既定 ~/.local/state/wordpress-bounty-harness 外 型付き event と digest 参照だけ。追記専用。
Private Evidence 同じ state dir の content-addressed store 外 候補本文、HTTP 捕捉、payload、画面、rollout、再現パッケージ、Verifier の http.json / steps.md / refutation.md、選定レポート、skip 診断。
継続運転の作業 file <state>/continuous.json / .pid / .log / .stop 外 runner の memo と停止マーカー。正本は台帳。
host 設定 Git 外 JSON（例の雛形は examples/translatepress-3.3.1/host.example.json） 外 docker、image digest、Codex runtime profile、認証 file のパス、Programme 写しのパス、履歴 mirror、legacyHistory.file。
認証 ホストの Codex auth.json（0600） 外 読むのは broker だけ。agent には使い捨ての grant token しか入らない。

5運転のしかた

CLI は AI と skill が叩く機械向けの interface（ADR 0032 Q27）。所有者は Claude Code の skill から操作し、台帳に書くコマンドは所有者が確かめて打つ。harness は pnpm build 後の node dist/cli/main.js で、--host（または WBH_HOST_CONFIG）と --state（または WBH_STATE_DIRECTORY）が要る。

継続運転（production runner）

harness continuous run    --host <host.json> --state <dir> --config <campaign.json> \
                          --selection <selection.json> [--campaign-prefix prod] [--verify-concurrency 1] [--resume]
harness continuous status --host <host.json> --state <dir>
harness continuous stop   --host <host.json> --state <dir>
harness continuous resume --host <host.json> --state <dir>
  • run は select → campaign run --all → 次の batch を回り続ける。止まる理由は 7 つ: operator の stop、候補枯渇、Programme 写し 35 日超、legacy JSON 欠落、下限別方針 file 欠落、例外 3 batch 連続、completed 0 の batch 3 連続。quota、拒否、ログイン失効（waiting-login）、disk 不足では止まらず待つ。
  • provider 上限は campaign-stopped(provider-limit) で止め、runner が backoff（quota 30→60 分、rate-limit 5→60 分、2 回連続で 6 時間）の後に同じ campaign ID で未消費の対象から再開する。
  • 対象単位の失敗（拒否 provider-cyber-policy、wall、schema、CLI 終了）は target-skipped で次へ進み、campaign を止めない。拒否を避けるために prompt を言い換えない。
  • stop は対象の境界で効く（進行中の対象は終わらせる）。停止マーカーは crash や再起動でも残り、resume か run --resume で解除する。SIGTERM は進行中 run を drain して終わり、マーカーは残さない。
  • 本番 checkout は detached worktree（/home/dev/wordpress-bounty-harness-prod*）。そこでの pnpm build は continuous stop の後だけ。

  1. 課題の生成（Harness）

    入口索引と保存先索引から「入口の群 × 対象内の種類」の短い課題を作る。1 課題 1 agent（子なし）、tool 回数と wall（例 10 分）に上限、同時 N。索引の穴は正規表現で追わず、短い solo agent（index-completion-v1、Lab なし）に埋めさせて origin: agent で併合する（#328、brief 1a-0〜1a-2）。

    全課題の出力を集約、正規化、run 横断の重複統合、coverage（observed / blocked / unvisited）を割り当てと突き合わせて記録。未処理の入口と欠けた辺の Lead を gapfill 課題として再投入し、増えなくなったら閉じる。

  4. 検証 consumer（探索と独立）

    verify next 相当の worker が台帳の未検証 Finding を 1 件引き、その Snapshot の Lab を 1 つ立てて判定器を回す。探索だけ流し続けても、検証だけ消化しても動く。

入口索引は正規表現で add_action / wp_ajax_* / REST route / shortcode のリテラル登録を拾うので、prefix 連結（Brizy で 90 件）、route 連結（SSA で 36 件、名前が / に潰れる）、自前 dispatcher（Unlimited Elements で call_user_func 30 件）の登録が落ちる。所有者の 7 件のうち入口がリテラルで載るのは 2 件だけで、3 件は producer が core（comment）や外部 API で plugin は「読んで描画する側」。方針は正規表現を完全にせず、unresolved 一覧を作って短い agent に埋めさせること。Issue #328；docs/evaluation/2026-10-18-index-baseline.md
refute 段（反証段）は何か 設計中
Lab の前に置く source だけの段で、別 prompt の agent が候補 1 件を潰しに行き、新しい候補は出せない。refuted は finding-parked(refuted) として Private Evidence に残し、upheld / undecided だけが検証に進む。判定器の確定ではないので runtime-confirmed には関与せず、開発セットで既知の型が落ちないことを gate にする。docs/reviews/2026-10-18-source-only-dispatch-design.md §4.4
なぜ judges は agent の自己申告を信じないか
LLM の合議が存在しない脆弱性を全員一致で支持した事例があり、本リポでも同じ Verifier が成立した書き込みを「反証」と書いた。確認は Lab が仕込んだ nonce 付き canary が回収されたかという機械的な事実だけにし、agent が「成功した」と言っても、リバースシェルや永続化を見せても証明にしない。だから Verifier は手順を整える役で、確定は Harness の判定器がする。docs/adr/0004；docs/adr/0031
なぜ reflected XSS は park されるのか
Wordfence が明示的に対象外にしており、Patchstack は条件付きで受理するが所有者が 2026-10-08 に「探索の目的にも提出候補にもしない」と決めた。判定器も作らない。mirror にある所有者名義の公開記録 28 件のうち reflected XSS は 7 件あり、だからこそ再発見 catalog からも除いた。半年後に見直す。docs/SPEC.md §8a；docs/adr/0032 Q2；docs/agents/measurement.md
なぜ検証の失敗を「偽」にしないのか
環境・手順・観測・証拠の不足で確認できなかったことと、主張が間違っていることは別で、前者を contradicted にすると本物を落として報奨を失う。だから incomplete は理由コードと次の手を持ち、理由ごとに有界の自動再試行をして、残りは人間の列に出る。docs/SPEC.md §2 不変条件 4；docs/adr/0022；docs/LESSONS.md 10
なぜ探索に最低時間を置かないのか
報酬が出た Lab は 2.1 時間で、5 時間超は全部成果なしだった（whitebox 世代）。v1.7 の 45 分下限なしでも v5 は同じ分類に届いたので下限を戻す根拠が無く、所有者も 2026-10-16 に「信憑性が無い」として外した。深さは時間ではなく、入口索引の全項目を記録してから閉じる条件（v6）で担保する。docs/LESSONS.md 3；docs/evaluation/2026-10-16-prompt-v5-comparison.md 読み取り 3；docs/adr/0029
既知 7 件の再発見で何が分かるか、何が分からないか
分かるのは配線（探索 → 保存 → 判定器）と分類ごとの判定能力。TP の ATO と stored XSS、SSA の SQLi と stored XSS は判定器で runtime-confirmed に届いた。分からないのは未知の発見率で、モデルが既知経路を記憶している可能性を除けないので、発見率の主張には使わない。docs/adr/0027；docs/evaluation/2026-10-16-wiring-gate-measurement.md
なぜ探索から Lab を外せるのか
探索と検証が同じ Lab に縛られていると、依存 plugin（Elementor、WooCommerce）で Lab が立たない対象は探索の機会そのものを失った（本番で 15 枠）。Lab を検証側だけにすれば、探索は source だけで並列に回し、Finding 1 件ごとに新しい Lab で判定器を回せる。runtime-confirmed の条件（同じ Snapshot、canary 回収）は変わらない。docs/reviews/2026-10-18-source-only-dispatch-design.md §0、§1；docs/adr/0029（2026-10-18 追記）
