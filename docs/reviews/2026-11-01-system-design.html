Bounty Harness 全体設計

選定から提出までを 1 つのシステムとして、段ごとに契約・処理・観測・決める数字を書く。2026-11-01。「調べて報告」の成果物で正本ではない。正本は docs/SPEC.md と docs/adr/。現行の処理は origin/main（8247631）のコードから読んだ事実、「変える処理」は案である。Finding の本文、payload、URL、対象固有の関数名は書かない。

いまのまま 変える 新しく置く 人間の判断点

担い手は 4 種類に分ける。Harness（TypeScript のコード。制御と記録だけ）、道具（script、semgrep、psalm。判断しない）、スキル（sandbox 内の agent が読む手順。中身の判断）、人間（観測、提出、承認）。

1. 設計の原則

凍結の 5 つ（ADR 0045）確定は人間の Lab 観測だけ。Harness は制御だけ。台帳は追記専用で digest 参照だけ。分母は Codex 1 時間あたりの Lab 発火と Wordfence の結果。設計変更は月 1 回。この設計書はこの 5 つを変えない。
1 段に 1 契約、1 観測、1 数字各段は、版付きの入力と出力の契約（Zod）、Harness が記録する観測、採否を決める数字を 1 つずつ持つ。観測は舵取りに使わない（ADR 0034）。
A / B / C の試金石合否を grep か AST で書けるなら道具（A）。足りないのが本体の保存欄などの固定知識なら知識表 + 追跡（B）。2 要求や 2 時点を並べないと決まらないなら推論（C）。提案は 3 つのどれを動かすかを先に言う。
スキル 1 本に単体テスト 1 つ探索のスキルは bench30 v3 の答え（Git 外）に対して、そのスキルの成果物だけで採点できる形にする。探索を丸ごと回さないと測れないスキルは置かない。
Lab で通った事実だけを次の土台にする候補はソース上で反証し、探索 Lab で Harness が捕捉した事実だけを次の仮説の入力にする。捕捉は「agent が観測した」と記録し、提出の確定は人間の観測に残す。
消し方を先に書くどの変更もスキル 1 本か設定 1 行で外せる。Harness のコードに探索の判断を戻さない（LESSONS 14）。

3. 段ごとの詳細設計

3.1 選定いまのまま担い手: Harness
役割
方針に従って対象を機械的に選び、同じ版は 1 Trial、版が上がったら戻す。
今の処理
  • WordPress.org の query_plugins を browse=popular と方針の tag（8 つまで）でページ順に読み、全件が最低インストール数を割ったページで止める。一覧が古いか取れないときは候補を空にする（wordpress-org-candidate-enumerator.ts:264-338）。
  • 適格性の理由は固定の語彙（excluded-slug、observation-stale、update-stale、below-installation-threshold、core-version-incompatible など。wordpress-selection.ts:233-309）。Programme の写しが current でなければ programme-stale。
  • 並びはインストール数の降順、同数なら版の公開日、slug（byInstall、l.106-114）。score はインストール数そのもの。
  • 台帳の除外: 数えられる Trial（explore / enumerate）があった slug@version は、版が上がらない限り previously-selected。理由は initial か version-increased（ledger-exclusions.ts:51-207）。
  • 方針の現在値: 最低 10,000 インストール、観測 2 日以内、更新 365 日以内、1 回に最大 5 本、WordPress 7.1.3（policy/selection.json）。
  • 書くもの: Private Evidence の selection-report.json、台帳の target-selected（selectionId、promptVariant）、target-skipped(stage: freeze)、campaign 起動時の selection-batch-bound。
変える処理

変えない。帯、順序、再訪の規則は所有者が 2026-10-31 に決めた。#724 の「差分監視」は選定の変更ではなく、version-increased で再訪した対象に対して「新版の差分を読む順の先頭に置く」というスキル側の手順である（§3.4 S1）。

観測と数字
対象ごとの Trial 数、再訪の数。採否の数字は持たない。
消し方
該当なし。
3.2 Snapshotいまのまま担い手: Harness
役割
対象 plugin、WordPress 本体、PHP ソース、依存 plugin を版と digest で固定し、以後のすべての段が同じ digest を参照できるようにする（不変条件 5）。
今の処理
  • freeze: 取得 → manifest（path、sha256、size の整列一覧）→ sourceDigest = canonicalDigest(manifest) → record の digest を snapshot digest にし、snapshots/<hex>.json に不変で書く。衝突は source-mismatch（src/snapshot/index.ts:195）。
  • ソースは sources/<sourceDigest>/ に 1 回だけ展開し、file は 0444。既存は再計測して digest 一致を要求する（materialized-sources.ts:56-127）。
  • 本体は固定 image の /usr/src/wordpress から取り、$wp_version を campaign の版と照合。PHP は image の php.tar.xz を sha256 で照合。
  • 依存: 主ファイル先頭 8 KiB の Requires Plugins と WooCommerce の版ヘッダから決める。pinned-only で固定の無い WooCommerce は header-derived-unpinned として外し、ほかの未固定は止める。pinset は wordpress-org/plugin-dependency-pins/<hex>.json に不変で置く。
  • #734: ヘッダ付き PHP が複数あるときは root の <slug>.php、無ければ root 直下に唯一のヘッダがある file、それ以外は main-plugin-file-ambiguous で延期。
  • 台帳: snapshot-frozen（sourceDigest、dependencyDigests）。
変える処理

変えない。bench30 の修正腕（全記録が直った最小の版）も同じ仕組みで固定しており、スキルの偽陽性の測定に使える。

観測と数字
freeze の失敗理由の分布（観測のみ）。
消し方
該当なし。
3.3 sandbox・broker・runtime変える（観測の追加と道具の同梱）担い手: Harness
役割
固定ソースを読み取り専用で agent に渡し、外向き通信を provider API に限り、制限時間と子の数を強制し、観測を取る。判断は持たない。
今の処理
  • runsc の container は --read-only --cap-drop=ALL --no-new-privileges --pids-limit=256、非 root、image は digest 固定、network は Trial ごとの internal network だけ（gvisor-container.ts:243-296）。代替 runtime は無い。
  • mount: /workspace/main（対象、RO）、/workspace/wordpress、/workspace/php、/workspace/dependencies/<slug>（RO）、/workspace/research（RW、Trial 内で共有）。全 mount を Snapshot の tree と再照合する。
  • broker: run ごとに 1 container。agent は Trial 限りの Bearer token だけを持ち、許す path は provider 1 種類分（Codex は /v1/responses か /backend-api/codex/responses、Claude は /v1/messages）。model が root か子の model 以外なら 403。要求数と大きさに上限。
  • Codex: codex exec --model … --sandbox danger-full-access（隔離は runsc 側）、--enable multi_agent -c agents.max_threads=<maxChildren> -c agents.max_depth=1。max_threads は同時に生きる子だけを縛る。Claude は PreToolUse hook で Agent を拒む。
  • skills: discovery.skills の id を digest 照合して CODEX_HOME/skills/<name>/SKILL.md（0400、.sh は 0500）に置く。8 本、各 32 KiB、支援 file 16 まで。
  • prompt の組み立て順: 目的文 → ## Finding and Lead output contract → ## Run parameters → ## Prior leads（任意）→ ## Trust boundary → ## Programme Boundary → ## Lab か「Lab なし」→ 本体・依存・notes の path → ## Assigned files（wordpress.ts:582-630）。
  • 観測: discovery-run-finished に observed{toolCalls, filesRead, uniqueFilesRead, labRequests, dbQueries}、usage（token 4 種）、wallTimeMs、childThreadsObserved/Admitted、brokerMetrics、researchArtifact{digest, truncated}。artifact は native-run-receipt、read-paths（rollout から取った source 相対 path の整列一覧）、research（/workspace/research の全件、8 MiB・256 entry まで）。
  • 子は Root の会話履歴を引き継いで始まる。bench30 v1 で入力 token の 79% が子の分。
変える処理
  1. 道具の同梱を確かめる。semgrep と psalm が sandbox image に入っているかは記録から判らない（bench30 v1 で実行 0）。入っていなければ image に足す。image digest が変わるので、campaign 設定で名指しし、台帳の configuration に image digest が残ることを確かめる。Harness は道具を実行しない。実行するのは S1 のスキルである。
  2. 被覆の観測を足す（舵取りではない）。run の終了時に、research archive の tools/hooks.tsv と tools/sinks.tsv の file 集合と read-paths の交わりを数え、observed.coverage{hooksFiles, hooksFilesRead, sinksFiles, sinksFilesRead} として discovery-run-finished に足す（欄は add-only）。さらに flows.tsv（§3.4）があれば行数、reaches / blocked / unknown の数、hop 数の分布を observed.flows に足す。Root には返さない。
  3. 子の履歴継承を測る。子ごとの入力 token は receipt にあるので、Codex 時間の分母に「子の継承分」を分けて出す。継承を切れるかは Codex の設定を調べてから決める。
契約
CampaignInput v1 は変えない。discovery-run-finished.observed に欄を足すだけ。旧 event は読み続ける。
観測と数字
被覆（hooks / sinks の file のうち読んだ割合。bench30 v1 の観測値は中央値 0.71 / 0.38）、flows の行数と判定の分布、子の token 比。
消し方
観測の欄を書く関数を revert。image は前の digest に戻す。
3.4 探索 Trial新しく置く（スキルの列と閉ループ）担い手: スキル（判断）、道具（列挙）、Harness（上限と記録）
役割
固定ソースから、対象範囲内の効果に届く経路を見つけ、契約の形で出す。何を読むか、どの順で仮説を立てるかはスキルの側にある（AGENTS.md「Harness と AI の責務」）。
今の処理
  • 目的文 wp2shell-bounty-v19-wide。Root は wbh-recon（地図）と wbh-tools（列挙 script 2 本と本体機能の固定参照）を読み、sink 分類（HTML / SQL / file / identity）ごとに 1 体の専門の子を立てる。子は入口から sink へ前向き、sink から入口へ後ろ向きに 1〜2 hop を追い、/workspace/research/<sink>.md に書いて戻る。Root は REGISTRY.md に hooks.tsv の読んだ行数と残りを書き、残り 0 で閉じる。
  • bench30 v1（48 Trial）の実測: Root は中央値 12 分で閉じる。48/48 が「残り 0」と書いたが、観測した被覆は sinks で 0.38。case の hit は 9/30（A 3/10、B 5/10、C 1/10）。外した 20 件は「読んだが Finding も Lead も無い」8、「Lead 止まり」12（欠けは producer が 28 件）。identity の子は平均 2.4 分で返り、Finding 1 件。
  • 探索 Lab を付けた腕（v14、6 Trial）は、Lab が立っても要求 0 だった。
変える処理

巨大な目的文で 3 種類の仕事をさせる形を、1 本ずつ単体で採点できるスキルの列に分ける。Root に残るのは順序と登録簿と終了だけ。Harness に残るのは子の上限、制限時間、Lab の予算、全件保存である。

スキル 種 入力 出力（research file） 単体テスト（bench30 v3 の答えに対して） 状態
S0 wbh-recon B/C 固定ソース recon-map.md（subsystem、入口、gate、helper、store、JS 境界） 答えの file が map の入口表か helper 表にあるか v1 あり

閉ループ

「Lab で通った」の意味を固定する。探索 Lab の POST /observe（役、path、操作 5 つまで、dialog marker）の答えと capture.jsonl は Harness が記録する事実で、exploration-lab artifact に残る。これを agent-observed と呼び、S6 の入力と Finding の labObservations にだけ使う。提出の根拠にはしない（凍結 1、ADR 0040）。人間は同じ要求を検証 Lab で再送して観測する。

反証の独立性について。Codex の子は Root の履歴を引き継ぐので、S4 を完全に独立した体にはできない。第 1 Trial では「候補を出した子の研究 file を読まない」「本体ソースの該当行を引用する」という手順で近似し、完全な独立は第 2 Trial の S5（別の sandbox、別の Trial）で取る。段 1b（§3.6）は、S4 との一致率が測れるまで残す。

3.5 出口（契約・正規化・park）変える（記録の形）担い手: Harness
役割
agent の報告をスキーマで正規化して受理し、Programme Boundary 外を park し、全件を Private Evidence に残す。棄却はしない（ADR 0018）。
今の処理
  • Finding（契約 v4、finding.ts:156-206）: claim（4,000 字まで）、attackerPosition（unauthenticated / subscriber / customer）、impact（22 種）、configurationPrecondition、brokenProperty、sourceTrace[{file, function, line}]、existingControls、labObservations、privateRecipeReference?。findingId は runId を含む本文の canonical digest。
  • Lead（lead.ts:25-65）: summary、primitive（read / write / delete / auth-material / partial-execution）、storage{kind, key} か null、missingEdge（producer / consumer / auth-use / reachability / precondition）、sourceTrace。
  • 正規化は構文の修復だけ（json-decoded、text-array-joined、text-truncated、impact-label-coerced、source-trace-parsed など）。スキーマに通らなければ candidate-held。
  • park: impact が Programme の 12 種に無ければ outside-programme-boundary。申告欄（v5 の 3 欄）が park 一覧に当たれば declared-precondition。v4 では申告欄を agent に見せないので、新しい Finding にはほぼ当たらない。
  • Root と子は別々に記録する。同じ経路でも runId が違うので別 Finding になり、群（file + 関数の組）で束ねる。
  • v5（申告欄付き）を使った v16 / v17 で Finding が崩れた（0.33 / Trial）。契約の文を足すと探索が縮む。
変える処理

消し方
export の節を外す。research file は agent の出力なので、スキルを外せば出なくなる。
3.6 選別（段 1、段 1b）変える（Trial 内の反証との関係）担い手: スキル（host 側、AI 操作役）

3.7 検証 Lab（verify next --handoff）いまのまま担い手: Harness（Lab と捕捉）、スキル wbh-verify（前提と route）
役割
Finding 1 件（同じ Snapshot のものを 1 Lab に 5 件まで）に使い捨ての WordPress + MariaDB を立て、スキルが通常機能で前提を作り、攻撃者の位置から route を実行し、Harness が HTTP と Lab 状態の差分と Lab browser の記録を残す。成立は判定しない。
今の処理
  • Lab は runsc。基準環境 hosting-default-v2（同梱 plugin なし、PHP 8、display_errors off、/%postname%/、未認証の攻撃者は foreign origin で /wp-admin（admin-ajax と admin-post を除く）、/wp-login.php、/xmlrpc.php を拒む）。初期化は core install → 同梱 plugin 削除 → 依存と対象の導入 → 基準の適用と読み戻し → 第 2 locale → 攻撃者と被害者の account → 初期記事（管理者の作者、#718）。

  • 結果は常に incomplete(awaiting-human-observation) で、evidenceCapture: harness-captured。不変条件 5 は Verification、台帳、Verifier の 3 か所で守る（Snapshot が違えば digest-mismatch）。
  • Lab は hold（既定 30 分、最大 1440）して人間の観測に使う（#600）。host 全体の slot は無く（#432）、Lab ごとの owner file だけがある。
変える処理

変えない。S5 で agent-observed の行がある Finding は、wbh-verify が前提と route を observed.tsv の行から組めるので、setup の時間が短くなるはずである。これはスキルの読む順の話で、Harness の変更ではない。所有者の「curl の要求を保存する」は proxy-capture.jsonl がすでにその形で、人間はこの要求を再送する。

契約

消し方
該当なし。
3.8 人間の観測と review人間の判断点担い手: 人間（観測の明言）、AI 操作役（記録の代行）、Harness（記録）
役割
確定の唯一の根拠を作る。保持した検証 Lab で、人間が用意された要求を送り自分のブラウザで見て、match / mismatch / unavailable を記録する（ADR 0040）。
今の処理
  • review observe: 現在の attempt が incomplete(observation | awaiting-human-observation) で、review-lab-reconstruction と manual-observation-lab-ready の receipt が一致し、--by が人間であることを要求する。--evidence（1 B〜10 MB）と任意の --ordinary-site yes|no --ordinary-site-reason を取り、manual-observation-recorded を書く。
  • review decide --reproduced match: 人間の --by と basis reproduce を要求し、human-reproduction-recorded と review-decided を書く。scope、draft、authorize はこの match を前提にする（submission-basis.ts）。
  • 代行（ADR 0040 追記 3）: 所有者が会話で結果と --ordinary-site を明言し、自分の画面を渡したときに限り、AI 操作役が所有者の名前で記録する。事前に manual-observation-attestations/<findingId>-<image digest>.json を Private Evidence に書く。これはまだ文書だけで、コードは無い。最終の accept、--prepared-by human、authorize は代行しない。
  • レビューの画面は wbh-review（Harness の事実だけを 1 画面に並べ、accept / reject / defer を提案し、--by ai で中間判断を記録）。
変える処理

規則は変えない。wbh-review の画面は、散文の claim より先に、結合した flows の行と proxy-capture.jsonl の該当要求（人間が再送する部品）を出す。所有者の「英文は短く」はここで満たす。attestation の file を書くコードが無い点は、代行を続けるなら小さな PR で足す（Harness の記録なので境界の内側）。

契約

観測と数字
match の数（分母の片側）。観測待ちの日数。
消し方
画面の順序はスキル本文なので revert で戻る。

3.10 台帳と Private Evidenceいまのまま（欄は add-only）担い手: Harness

5. 所有者の判断点

  1. #724 の読み替え。「掃き出し層が候補を大量に出し AI が確認する」から、「道具は A の候補、知識表は B の入口、AI は追跡・反証・推論。それぞれ単体で採点」へ。11 月の 1 回の設計変更はこの形で使う、と所有者の言葉で決める。

  3. 段 1b の縮退の線。S4 との一致率が何件・何 % で段 1b を確認票に縮めるか。
  4. 第 1 Trial と第 2 Trial の配分。Lab 付き第 2 Trial は同時 2 本から（ADR 0044）。Codex 5 席のうち何席を回すか。
  5. 目的文の削除。「sink 分類ごとに 1 体」と停止段落を削った版は、新版ではなく削除版として扱う（凍結 5 の「消す方向」）。この解釈でよいか。
