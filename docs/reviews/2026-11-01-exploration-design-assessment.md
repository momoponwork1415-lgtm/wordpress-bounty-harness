# 探索設計の現状評価と変更の指針（2026-11-01）

「調べて報告」の成果物で、正本ではない。正本は docs/SPEC.md と docs/adr/。所有者の問い（2026-11-01）: 「AI の案に乗って改善を進めているが、自分がその方向でよいという指針を持てていない。現状がどうなっていて、何をどう変えるべきで、なぜそれがこの Harness を良くするのかを理由付きで。良いところと悪いところも。探索の形が多すぎて整理できない。何があれば安定して探せるか。記録を英文ではなく機械的に読める形にし、Lab で HTTP 要求を保存する方がよいのではないか」。

Finding の本文、payload、URL、関数名は書かない。数字はすべて既存の記録（台帳、Private Evidence、docs/reviews、docs/evaluation、Issue）から引いた。

## 0. 結論を先に

1. **土台は正しく、揺れているのは探索の中身だけである。** Snapshot、gVisor、台帳、Lab、人間の観測、提出の流れは 2 週間で一度も崩れず、CVE 級 5 件と報酬 1 件を出した（ADR 0045 背景）。揺れたのは探索 mode（2 つ作って 2 つ廃止）とプロンプト（5 回）で、その間の本物の率（段 1b を通る Finding / Trial）は 0.05〜0.07 のまま動いていない。
2. **揺れの原因は、1 本のプロンプトに 3 種類の仕事を同時にさせていることにある。** 3 種類とは、道具で決まる仕事（A）、固定の知識表と追跡で決まる仕事（B）、推論と時間が要る仕事（C）である（分類は [noticing-vs-reasoning](2026-11-01-noticing-vs-reasoning.md)）。プロンプトを変えると 3 つへの注意の配分が動くだけなので、Finding と Lead の数が入れ替わる「シーソー」にしか見えない。
3. **変更の指針は 3 行で持てる。** (a) 道具で書ける合否は道具に出させ、AI は読む側に回す。(b) 推論ではなく知識で決まる部分は知識表として固定し、AI に渡す。(c) 推論が要る部分だけに強いモデルと時間を使い、プロンプトの言い換えでは触らない。どの提案もこの 3 行のどれに当たるかを先に言わせ、言えない提案には乗らない。
4. **AI の提案に乗ってきた不安は正当である。** ADR 0045 の背景 5 は「AI が設計案を安く出し、所有者が速く go を出し、提案から実装まで数時間」と書いている。本報告もその AI の 1 つが書いている。だから、本報告の提案も §7 の数字で採否を決める形にした。

## 2. 良いところ（残す）

1. **土台が崩れない。** Snapshot と digest、gVisor、台帳、Lab、人間の観測、提出は 2 週間で無事故。これが「月 1 回の設計変更」を安全にしている。
2. **Harness は制御だけ、中身はプロンプトとスキル、digest で固定。** だから版の比較ができ、過去の Trial を照合でき、失敗した案を revert で戻せる。過去 4 世代はここで肥大して死んだ（LESSONS 14）。
3. **選別は出口の gate で行い、プロンプトで絞らない**（LESSONS 1、ADR 0018）。契約 v5 で絞る文を足して Finding が崩れたとき、原因が特定できたのはこの規則があったからである。
4. **測る道具が揃っている。** bench30（答え付きの密な版）、noticing-vs-reasoning（A/B/C）、構造調査、read-paths。「何が効いたか」を数字で言える土台はもうある。今足りないのは数字ではなく、数字を層ごとに分けて読むことである。
5. **出力契約に構造がある。** `sourceTrace[{file, function, line}]`、`impact`、`attackerPosition`、Lead の `storage{kind, key}` と `missingEdge` は機械で読める。ADR 0044 の群（入口の file + 関数、効果の file + 関数の組）はこの上で動いている。§4.6 の「機械的に読める記録」は、ここを広げれば足りる。
6. **AI が答えの file には届いている。** bench30 で 48/48、見逃し 13 件で 10/13。「読んでいない」が原因の時代は終わっている。

## 3. 悪いところ（直す）

1. **1 本のプロンプトが A / B / C を全部担う。** その結果、v14 → v16 → v18 → v19 の差は「Finding にするか Lead にするかの境目」だけで、本物の率は動かなかった（構造調査の表）。これが所有者の言う「FP と FN の入れ替えしかできない」の正体である。
2. **終了条件が自己申告で、観測と一致しない。** 48/48 が「残り 0」と書き、観測は sinks.tsv の 0.38。Root は制限時間の 1/8 で閉じる。文を足して縛ろうとした v19 の停止段落も縛れていない（bench30 v1 §4）。
3. **Lead を Finding へ詰める段が無かった。** 外した 20 case の 12 が Lead 止まりで、欠落は `producer`（攻撃者がその値を置けることを示せない）が 28 件。見逃し 4 件も同じで、他人は同じ前提のまま公開まで持っていった。ADR 0044 はこの穴を塞ぐ設計だが、まだ数字が無い。
4. **入口側の知識が無い。** `core-fixed-list-v1.md` は「本体が値をどう効果にするか」（sink 側）の表で、「低権限者が本体のどこに値を保存できるか」（source 側）の表は無い。成立した B の 14/20 がその source を入口にしていたのに、プロンプトは「user profile and registration fields」「comments」を入口一覧の中で一語ずつ挙げるだけである。所有者の体感（ニックネーム欄や本体の標準機能が糸口）は記録と一致する。
5. **A 型を AI の注意に任せている。** bench30 の A 群は 3/10、benchmark の SQLi 2 件は 0/2、sql の子は 88 体で Finding 2 件。list は hint として置いたが、semgrep / psalm は 0 回走り、script の pattern の欠け（`$wpdb->insert/update`、`->wpdb->`、JS の sink）は分かったまま直っていない。A は市場の 43%、所有者の実績の 47% を占める。
6. **記録が散文に寄っている。** Finding の `claim` は最大 4,000 字、`existingControls` と `labObservations` も散文。レビューする人間は英文を読んで入口と sink と欠けを自分で抜き出している。機械で読めるのは `sourceTrace` と列挙型だけで、「どの parameter が、どの変換を経て、どの store を通り、どの sink に、届く / 届かない」は表になっていない。
7. **子が Root の履歴を引き継ぐ。** token の 79% が子で、子の wall は中央値 2.8 分。「短い子を多数」の形にはなっているが、1 体あたりの費用は短くない。分母を Codex 時間にするなら、ここは測って決める値である。
8. **決定の速度が速すぎた。** 提案から実装まで数時間、2 週間で mode 2 つと版 5 つ。ADR 0045 がこれを月 1 回に縛ったのは正しい。本報告の提案もその枠の中で、数字を先に取る順に並べる（§7）。

## 4. 変更の指針（理由付き）

### 4.0 見分けの試金石

「その合否の基準を、プラグインのソースだけに対する grep か AST の問い合わせとして書けるか」。

- 書ける → **A: 道具の仕事。** AI は道具の出力を読む側に回る。
- 書けないが、足りないのは「WordPress 本体や典型的な設定が何を保存し何を描くか」という固定の知識 → **B: 知識表 + 追跡。** 表は人が書き、追跡は AI がする。
- 2 つの要求や 2 つの時点を並べないと決まらない、識別子の意味、状態遷移、決済 → **C: 推論の仕事。** 強いモデル、面ごとの時間、Lab での反証。

所有者の問い「AI が見落としたら発見できないのでは」への答え: どの設計にも見落とし集合はある。違いは、その集合を**列挙できて縮められるか**である。道具の見落としは 4 つの型として列挙できていて、pattern を足すたびに縮む。AI の見落としは列挙できず、5 版の言い換えで縮まなかった。だから A は道具に出させる。ただし道具は AI の代わりではなく追加である。AI が全ソースを読む経路は今のまま残し、道具の候補を**読む順の先頭**に置くだけなので、AI だけのときより見落としは増えない。

### 4.1 A: 道具が候補を出し、AI が読む

- 変えること: sandbox の中で semgrep / psalm taint と列挙 script v3（`$wpdb->(insert|update|delete|replace)`、`->wpdb->`、本体の書き込み関数、JS の `v-html` / `.html(` / `innerHTML`）を Root が実際に走らせ、その候補行を sql / file / html の子の読む順の先頭に置く。これは `wbh-tools` の支援 file と本文の変更で、Harness のコードは変えない。
- なぜ効くか: A の合否は taint の定義そのもので、道具には FP / FN のつまみが無く、再現率だけがある。bench30 の A 群 53 記録で再現率を測れば「何件が道具で拾え、何件が AI に残るか」が数字で出る。AI の注意は B と C に回せる。
- 決める数字: ホスト側で bench30 A 群 12 本の脆弱版に semgrep / psalm と script v3 を掛けた再現率（道具だけ、AI なし、token 0）。これが v19 の A 3/10 を上回らなければ、この行は消す。

### 4.2 B: 入口側の知識表を固定し、子を表の行に当てる

- 変えること: 「低権限者が WordPress 本体と主要な依存に保存できる欄」の固定参照（`core-stored-sources-v1.md` のような名前。コメントの本文・作者名・URL・User-Agent、表示名・ニックネーム・自己紹介・URL、登録欄、再設定メール、front-end の投稿フォーム、WooCommerce の請求先と注文メモとレビュー、検索語の記録、など。プラグイン名は書かない）を `wbh-tools` と同じ置き方でスキルの支援 file に置く。html の子は、この表の各行から sink へ後ろ向きに追う 1 行 1 単位の仕事を受け取る。
- なぜ効くか: 成立した B の 14/20 はこの表の行から始まる。これは推論ではなく知識で、AI が毎回思い出すか忘れるかに任せている。表にすれば忘れない。所有者の問い「リファレンスとして置くべきか」の答えは yes で、置き場はプロンプト本文ではなく支援 file である（本文に足すと Finding が減る。ADR 0039 追記 12・14）。
- 守ること: agent に渡る文章なので owner-approved。出典対照表に無い要素は足さない。
- 決める数字: bench30 B 群 10 本（125 記録）の hit が v1 の 5/10 からどう動くか。

### 4.3 C: 推論の仕事には時間と面を与え、プロンプトでは触らない

- 変えること: 名指しの深掘り（#724 の 3 つ目）を C 専用にする。identity、決済、cron、キャッシュ、nonce と token のように状態を持つ面を地図から列挙し、面ごとに子 1 体と時間を割り当て、ADR 0044 の Lab 付き第 2 Trial で反証させる。
- なぜ効くか: 見逃しの C 6 件は file を開いていた。足りないのは 2 要求・2 時点を並べる時間と反証の手段で、文言ではない。identity の子が 2.4 分で返っているのは、「sink を読み切る」仕事として渡しているからである。
- 正直に書くこと: C に安い近道は無い。bench30 の C 群 1/10 は、強いモデルと時間を使っても大きくは動かない可能性がある。ここでプロンプトの版を重ねない。

### 4.4 終了条件: 自己申告を観測に置き換える（舵取りはしない）

- 変えること: Harness は「列挙出力に載った file のうち read-paths に現れた割合」と「Root の自己申告の残り行」を観測として記録し、trial-timeline と scorer に並べる（bench30 v1 §8 の 6）。終える判断そのものはスキルの手順（#686 の `wbh-coverage` 案）に置き、Harness の床は増やさない。
- なぜ効くか: 今は自己申告と観測の差が記録に出ていないので、どの版が「本当に読み切った」かを比べられない。観測が出れば、最低時間を置く腕（bench30 v1 §8 の 3）と置かない腕を同じ尺で比べられる。
- 決める数字: bench30 v3 で最低時間 0 / 60 の 2 腕の被覆と hit。

### 4.5 Lead → Finding: ADR 0044 を bench30 の 12 case で測る

- 変えること: 新しい設計は要らない。Lead 止まりの 12 case に第 2 Trial（Lab 付き、Prior leads 節）を回す。
- なぜ効くか: 欠落の 28 件が `producer` で、第 2 Trial はまさに「攻撃者がその値を置けるか」を Lab で確かめる場である。
- 決める数字: 入力した Lead の群のうち Finding になった数。

### 4.6 記録の形: 散文を減らし、流れの表と HTTP 要求を残す（所有者の追加の問い）

所有者の案は 2 つに分かれる。どちらも方向は正しいが、置く場所を間違えると契約 v5 の二の舞になる。

**(1) 関数単位で機械的に読める記録。**

- 変えること: 子が書く研究 file に、流れの表（`/workspace/research/flows.tsv`）を足す。1 行 = 入口（file:関数:行、機構、誰が到達できるか）、parameter か保存欄、経由する変換（sanitizer と文脈）、store（kind, key）か無し、sink（file:関数:行、分類）、判定（届く / 遮られる / 不明）、欠け（missingEdge と同じ語彙）。全件保存される research artifact なので、出力契約 v4 は変えない。
- なぜ効くか: 契約に欄を足すと Finding が崩れた前例がある（v5）。研究 file なら探索の出口を締めず、人間と scorer は表だけ読める。ADR 0044 の群の鍵（入口と効果の組）とそのまま揃う。
- 次の段: 表の埋まり方を 20 Trial で測ってから、契約へ昇格させるかを決める。昇格は「散文の欄を短くする」方向（`claim` の上限を下げる）とセットで、文を足す方向にはしない。

**(2) Lab で curl の要求を保存し、英文は短く。**

- 事実: 検証ではすでにその形である。`verify next --handoff` の Lab は HTTP を捕捉し、人間の観測は「用意した要求を送って自分のブラウザで見る」（所有者決定 2026-10-26）。
- 探索に付けた Lab は使われなかった（v14 で要求 0。Root は 16 分で閉じる）。ADR 0044 が「第 1 Trial に Lab を付けない」としたのはこのためである。
- 変えること: HTTP 要求を保存する場は第 2 Trial（ADR 0044、Lab 付き）と検証に置く。第 1 Trial には付けない。Finding の `claim` は、要求が保存されている場合は要約 1 段落で足りるよう、レビューの画面（`wbh-review`）が要求の方を主に出す。
- 守ること: AI が送った要求と見た応答は確定の根拠にしない（凍結 1、ADR 0040）。保存した要求は「人間がそのまま再送する部品」であって判定ではない。この線を越えると判定器に戻る。

### 4.7 所有者が持つ指針（AI の提案を受けるときの 3 つの問い）

1. その提案は A / B / C のどれを動かすか。1 つに言えないなら、またシーソーを揺らすだけである。
2. 採否を決める数字は何か（bench30 v3 の群別 hit か、本番の Codex 1 時間あたりの Lab 発火か）。数字を先に言えない提案は見送る。
3. それは道具の変更か、知識表の変更か、推論の配分（時間、モデル、面）の変更か。プロンプトの言い換えなら、凍結 5「消す方向にしか触らない」に反する。

## 5. 探索の形の整理（形が多すぎて整理できない、への答え）

| 形 | 向き | 得意な型 | 公開の例 | この Harness での対応物 |
| --- | --- | --- | --- | --- |
| sink 起点の流れ作業: 道具が sink を列挙 → 安いモデルが絞る → 後ろ向きに到達性を追う → 強いモデルが悪用まで組む | 後ろ向き | A、B の sink 側 | AVDH（Flash Lite が入口を列挙 → 強いモデルが検証）、Mantis の構造索引（HINT として tool）、Kinorth の正規表現 | `wbh-tools` + sql / file / html の子。ただし道具は走っておらず、子は候補なしで両向きに読む |
| 入口起点の仮説検証: Root が地図から仮説を立て、子が検証する | 前向き | C、横断的なもの | wp2shell v1.7 / v8、Anthropic 参照 harness の recon → find、Cloudflare skill | v19 の Root + 子の形そのもの |
| 差分起点: 新版の差分だけを規則に通す | どちらも | 全型だが面が狭い | 所有者の 32 件中 10 件が修正版の後の再訪 | #724 の 2 つ目。未実装 |
| Lead の前進: 前回の欠けを名指しして読み直す | 後ろ向き | B | 先例なし（Cloudflare の gapfill が近い） | ADR 0044。実装済み、未計測 |

「dutafi のように semgrep で sink を列挙し sonnet で絞り opus が悪用を組む」という形は、dutafi 本人は手法を公開していない（[ハンター調査](2026-10-25-wordpress-bug-hunter-methods.md)）。その流れ作業は AVDH と Shopify の記事に出てくる形で、人の名前ではなく「sink 起点の流れ作業」として覚えるのが正確である。

v19 が中途半端に感じられる理由はこの表で説明できる。子を sink 分類で切っているので形は sink 起点だが、道具の候補を受け取らず、Root は仮説も立てない。**どちらの形の強みも使っていない。** 直し方は、sink 起点の枝には道具の候補を流し（A）、入口側には知識表を流し（B）、仮説検証の形は C の面にだけ使う、という分け方である。

## 6. 何があれば安定して探せるか（道具）

優先順に。どれも Harness の判定器ではなく、agent の道具か観測である。

1. **semgrep / psalm taint と script v3 が sandbox で実際に走ること。** いまは 0 回。閉じる穴は A。測り方は §4.1。
2. **本体保存欄の source 表**（§4.2）。閉じる穴は B の入口。
3. **観測した被覆の記録**（§4.4）。閉じる穴は終了条件の自己申告。
4. **流れの表 `flows.tsv`**（§4.6 (1)）。閉じる穴は散文の記録とレビューの負担。
5. **Lab 付き第 2 Trial と HTTP 捕捉**（§4.5、§4.6 (2)）。閉じる穴は `producer` の欠けと、人間が再送する部品の不足。
6. **版の差分器**（#724 の 2 つ目）。閉じる穴は「どこを読むか」の注意配分。

置かないもの: 判定器、canary、Harness の床、プロンプトの新版。いずれも凍結 5 つに反するか、過去に成果を作らなかった。

## 7. 次の 1 手（数字を先に取る順）

1. **bench30 v3 を走り切らせる**（いま走っている）。A / B / C 群別の hit が、以降のすべての比較の基準線になる。
2. **ホスト側で bench30 A 群 12 本に semgrep / psalm と script v3 を掛ける。** AI を走らせず、token 0、設計変更にならない。道具だけの再現率が v19 の A 3/10 を超えるかで §4.1 を決める。
3. **source 表と `flows.tsv` の雛形を支援 file として起こし、owner-approved に出す。** B 群で測る。
4. ADR 0044 の第 2 Trial を Lead 止まりの 12 case に回す。

この 4 つはどれも #724 の枠（11 月の 1 回の設計変更）の中に収まり、Harness のコードは観測の追加（§4.4）以外に触らない。
