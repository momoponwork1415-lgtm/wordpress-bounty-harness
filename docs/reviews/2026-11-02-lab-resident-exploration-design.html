Lab 常設探索の設計 — Lead を実行環境で前に進める

所有者の問い（2026-11-02）: 「Codex から Lead が出て、それを検証しなければならないのだから実行できる環境は必須。改善案を出して」。この文書は Claude が設計し、所有者がレビューする。

2026-11-02関連: #791 #715 #724 ADR 0043 / 0044 / 0045 / 0048正本ではない（docs/reviews）

1. いまの事実

Lab はいつ付くか

  • 第 1 Trial（本番・bench とも）: Lab なし。固定ソースだけを読む。
  • 第 2 Trial（Lead 入力、ADR 0044）: Lab 付き。名指しで回している。
  • 検証（verify next --handoff）と人間の review Lab: Lab 付き。

Lab で今できること

  • HTTP で site に届く。visitor / 低権限 / administrator のアカウント。
  • POST /reset（回数制限）、POST /observe（headless browser で 1 ページ、alert マーカー、回数制限）。
  • 無いもの: DB 読み取り（labAccess.database は "none" 固定）、入力値の保存先検索、PHP の実行トレース。
  • Harness は reset ごとの site 状態（options、users、table の行数と checksum）を記録しているが、エージェントには見せていない。

取り逃しの形（bench h31、20 plugin、62 record）

到達 件数 止まり方

Lead 止まり 20 「攻撃者の入力がここに来る経路（producer）が見つからない」か「sink が出力に届くか読み切れない」。コードだけでは決まらない問いが大半。

Lead 止まりの 20 件と、本番 leads2 の Lead 160 件の大半が、同じ「入れた値がどこへ保存され、どこで読まれるか」で止まっている。これは実行して観測すれば 1 回で決まる問いである。Root は 120 分のうち 30〜40 分で閉じていて、時間は余っている。

2. 方針（変えないこと）

  • Harness は判定器を持たない。Lab の観測は事実であって確定ではない（不変条件 3）。確定は人間の review Lab のまま。
  • 探索は広いまま。対象外の impact は出口で park し、落とすのはレビュー側（前回答のとおり）。
  • 1 Trial 1 Lab。Lab の使い回しはしない（不変条件 5、隔離）。
  • Harness のコードに「エージェントにこう探させる」は入れない。足すのは観測器と選定の規則だけ。読み方はスキルが持つ。
  • 凍結 5 項目（ADR 0045）は触らない。本設計は所有者が 11 月の設計変更として名指ししたものと解釈する。

3. 設計

A. Lab を全 Trial の既定にする Harness: 設定と同時数

  • discovery.lab の既定を attached にし、bench と本番の設定で有効にする。Lab の記述は既存の ## Lab 節のまま。
  • 同時数は Lab 1 基の実メモリを測って決める（leads2 では Lab 付き 2 並列で回った。Codex sandbox は 250〜350 MiB、Lab は WordPress + MySQL の 2 コンテナ）。host 54 GB の予算の中で、Lab 付き 4〜6 並列を目標にする。

B. Lab の観測器を 3 つ足す Harness: 観測、判断なし

観測器 問い 形 実装の足場
POST /find 入れた印はどこに保存されたか body は印の文字列（10〜15 桁の数字、observe の dialogMarker と同じ形）。答えは DB の {table, column, 行の主キー} と、wp-content 配下の {file path} の一覧。回数制限つき。 既存の state-capture の MySQL 経路（table 一覧と query）と、Lab コンテナ内の文字列検索。
POST /sql その行には何が入っているか、どの option が変わったか SELECT 1 文だけ、読み取り専用ユーザー、行数上限。labAccess.database: "read-only"（型は既にある）を実装で埋める。 state-capture と同じ接続。読み取り専用ユーザーを Lab 供給時に作る。
POST /trace このリクエストで plugin のどの関数がどの順に走ったか body は role と path と任意の POST body。Harness が Xdebug の function trace を有効にして 1 リクエストを送り、plugin 配下の file:line の呼び出し列（行数上限）を返す。所有者の言う「ブレークポイント」のバッチ版。 Lab image に Xdebug を入れ、trigger 方式で Harness だけが有効化する。通常のリクエストには影響しない。

3 つとも、答えは observe と同じく Private Evidence に記録し、Finding / Lead の labObservations に書かせる。Harness は結果を読まない。文言は ## Lab 節に 3 段落足す（agent 向け本文なので owner-approved）。

C. Lead が残った Trial は第 2 Trial を自動で組む Harness: 選定の規則

  • 規則: 「終了した Trial に Lead が 1 件以上あり、同じ Snapshot に第 2 Trial がまだ無ければ、次の選定で第 2 Trial を 1 回組む」。Lead の中身は読まない（件数だけ）。ADR 0044 の重複拒否がそのまま上限になる。
  • 第 2 Trial の入力は現在と同じ: Lead 入力 + 前回の研究 file + Lab。設定 discovery.followUp: "leads" のような 1 項目で on/off。
  • Lead は引き続き review leads で人が全件見られる。検証列に入るのは Finding だけ、という線は変えない。

D. 研究 file の引き継ぎを広げる Harness: ADR 0048 の拡張

  • 今渡しているのは recon-map.md と lab-setup.md。これに research/assumptions（v1）、research/walks（v2）、/find の答えを Harness が集めた保存先の表（marker → table/column/file）を足す。
  • 同じ plugin の新版 Trial は、旧版の表から「ここに保存される」を前提にせず再確認する（ADR 0048 の「別版の記録」注記のまま）。これが所有者の「旧版の探索結果を最新版で再利用」に当たる。

E. スキル側 プロンプト・スキル

  • wbh-falsify の Store 行と Transformation 行: Lab があるときは /find と /trace の答えで「enforced at」を埋める。コードの推定だけで埋めない。v2 の計測（h32）の後に v3 として 1 回で入れる。
  • 第 2 Trial のスキル（Lead 入力）: Lead の producer を後ろ向きに探す手順を 1 段足す（leads2 の Lead 160 件の大半が producer 欠けで止まった事実に基づく）。
  • 目的文の手順段落（sink 種別で子を分ける段落、hooks.tsv の行数で閉じる段落）は削除のみ。sink 軸と subsystem 軸の二重を解く。

4. 順序と計測

# PR（問い 1 つ） 計測 合格線
0 h32: wbh-falsify v2、Lab なし（実行中） 6 対象 37 record F ≥ 15（h30 12 / h31 10）
1 A + B の /find と /sql + ## Lab 節の追記 h33: 同じ 6 対象を Lab 付きで F が h32 を上回り、Lead 止まりが減る。分母は Lab 発火 / Codex 時間
2 B の /trace（Lab image + エンドポイント） h34: 同じ 6 対象 Transformation 系（HTML 書き換え 6 件の形）の到達が増える
3 C 自動の第 2 Trial 本番 2 週 Lead → Finding の転換が Codex 時間あたりで leads2（4 F / 14 Trial）を上回る
4 D 研究 file の拡張 同じ plugin の新版が出たとき 新版 Trial の Root 時間が短くなり F が落ちない
5 E スキル v3 と目的文の削除 各 1 回の bench 6 段の採否規則のまま
— 制限時間 120 分の上限を上げる Closing が「wall で終わった」と言う Trial が出てから それまで上げても効かない

費用: Lab 付きで Codex 時間は plugin あたり 1.5〜3 倍。所有者の「探索時間が延びてもいい」を前提に、分母は Lab 発火 / Codex 時間のまま見る。

5. 限界と見送るもの

  • Lab は「典型的な site」1 つなので、設定依存の経路は administrator の操作で前提を作る形のまま。前提は configurationPrecondition に残り、段 1 で選別する。
  • 観測器が増えるとコードを読む量が減る可能性がある。unique-file 比率を Trial ごとに見続ける。
  • Argus 級（長時間・多手法）の形は本設計の外。所有者決定どおり見送る。
  • 提案しないもの: Harness が Lead を判定すること、探索の目的文を狭めること、plugin 別のシナリオ、Harness 側の最低時間。

6. 消し方

  • A: 設定の既定を none に戻す。
  • B: 3 エンドポイントと ## Lab 節の 3 段落を消す。Xdebug は image から外す。記録済みの観測は読み続ける。
  • C: followUp を外す。組まれた第 2 Trial の台帳は残る。
  • D: 渡す file の一覧を 2 つに戻す。

7. レビューしてほしい点

  1. 観測器 3 つの範囲。/sql を読み取り専用で渡すことに不安はないか（Lab は使い捨て、外向き通信なし）。
  2. C の規則「Lead ≥ 1 なら第 2 Trial 1 回」でよいか。費用を抑えるなら「Lead ≥ 2」か「Finding 0 かつ Lead ≥ 1」。
  3. 順序。1（find/sql）を 2（trace）より先にする理由は、実装が軽く、Lead 止まりの大半が保存先の問いだから。
