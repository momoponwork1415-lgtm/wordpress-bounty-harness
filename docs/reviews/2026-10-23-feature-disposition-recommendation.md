# 28 機能の採否と責務の推奨

2026-10-23。[機能一覧](2026-10-23-current-feature-inventory.md)の F01〜F28 を分類する。根拠となる実装は main `2a8e7e25e157e34afbeded94f67f14c090de4991`。本資料は提案であり、採用決定・正本の改訂ではない。コード、設定、スキル、実データは変更しない。

## 前提

現在の目的である「無人運転で候補と証拠を残し、人間が確認・提出する」を続ける前提で分類する。無人運転自体をやめる場合は F05 等の結論が変わる。今回は本番設定・操作頻度の追加調査をしていないため、到達可能な機能を未使用とは断定しない。

- **ハーネスに残す**: その責務をコードで保証する。現在の実装全体を温存するという意味ではない。
- **スキルに任せる**: 文脈を読む判断・比較・執筆を AI 側に置く。形式検査、記録、証拠の照合、人間の承認まで AI の自己申告に移さない。
- **簡素化する**: 必要な目的を残し、操作・責務・表示・運用負担を小さくする。具体的な削除範囲が確定したという意味ではない。
- **そもそも削除する**: その旧機能の実行経路を退役させる。共有基盤や保存済みの記録を一緒に消さない。

主分類は **残す 16、スキル 2、簡素化 9、削除 1**。28 機能の中には複数の役割が入っているので、主分類と残す部分を併記する。機能数はコード量の削減率を示さない。

## ハーネスに残す — 16 機能

| ID | 機能 | 推奨理由と残す責務 |
| --- | --- | --- |
| F01 | 対象候補の収集・選定 | 人間が決めた方針の適用は定型処理。手動指定と自動選定を持つ現在の運用を維持する前提。個々の採点項目の有効性まで確認したという結論ではない |
| F02 | ソース取得・版固定 | 何を調べた結果かを後から照合する土台。同一性の保証を AI の説明だけに依存させない |
| F03 | AI の起動・出力回収 | 実行開始・終了と出力の対応を確実に残す。AI の調査内容をコードで指示する責務は含めない |
| F05 | 単発・無人の連続運転 | 現在の無人運転という利用目的に必要。後段スキルを全自動で連結する新機能まで含めない |
| F07 | 時間・人数・資源の制御 | 上限と観測は機械的に守る必要がある。最低活動時間などの運用方針の値・適否は、この分類だけで変更しない |
| F08 | 隔離・通信・認証情報管理 | 実行環境と資格の管理は文章上の約束だけでは保証できない。実行を維持するなら同等の保証を持つ |
| F09 | 出力の形式検査・正規化・保留 | 決まった形式の検査と保存は定型処理。形式が不十分な候補を失わない責務も残す |
| F10 | 対象範囲外の振り分け | 人間が決めた明示的な制限を出力側で適用し、理由を記録する。規則の文脈解釈とは分ける |
| F11 | 確認用 Lab の準備・片付け | 環境の寿命と資源を一貫して管理する責務。対象固有の作業手順を抱え込まない |
| F12 | スキルとの受け渡し | 入力・出力・失敗状態の契約はハーネスが持つ。スキルの仕事の内容をこの層へ重複実装しない |
| F13 | 観測・証拠に基づく判定 | AI の主張と観測事実を分離する責務。確認済みという結果の意味を一定に保つ |
| F15 | 最新版・別版の結果管理 | 異なる版の結果を混ぜず、元の候補との対応を残す。作業方法の解釈はスキル側 |
| F18 | 採用・棄却・保留の記録 | 判断者・理由・根拠の記録は定型処理。中間の判断案は AI、最終査読は人間 |
| F20 | 人間用 Lab・手動確認の記録 | 人間が確かめるための環境と記録を提供する。実際の確認を AI に代行させるという分類ではない |
| F23 | 台帳・非公開資料の保管 | 証拠、判断、版の対応を保ち、あとで追跡するための基盤。保管先の実装は置換できるが責務は残る |
| F26 | テスト・静的検査 | 開発基盤として残す。製品の運転中に行う機能とは分ける。不要になった機能専用の検査は、その機能と一緒に整理する |

## スキルに任せる — 2 機能

| ID | 機能 | スキル側に置くもの | ハーネス・人間側に残すもの |
| --- | --- | --- | --- |
| F19 | 重複照合・提出条件・提出先の整理 | 公開情報の比較、同じ問題かの解釈、規則の文脈・例外の解釈、提出先の提案 | 検索、明示的な条件の照合、結果・根拠・時点の保存はハーネス。権限や対象範囲の変更、最終的な提出判断は人間 |
| F21 | 報告文・添付一覧・文案管理 | 英語の文案、説明、添付一覧、入力用資料を作る仕事 | 文案と添付の参照、版、作成者属性、承認対象との対応はハーネス。内容の最終確認は人間 |

理由は、比較・解釈・執筆には文脈が必要だからである。現在も大部分はスキルが担当しているので、これから全面移管して大量のコードを消せる、という見積もりにはしない。

F19 は規則ごとに所有者を明確にする。確定した条件の照合までスキルへ移すと、同じ入力でも記録の意味が揺れやすい。一方、自然言語の例外や個別事情の解釈をコードへ増やすと、方針と実装の二重管理が増える。

根拠: [現行 Review 手順](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/blob/2a8e7e25e157e34afbeded94f67f14c090de4991/src/review/README.md)、[コード側の提出条件照合](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/blob/2a8e7e25e157e34afbeded94f67f14c090de4991/src/profiles/wordpress/scope-policy.ts#L101)、[文案保存](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/blob/2a8e7e25e157e34afbeded94f67f14c090de4991/src/review/index.ts#L815)。

## 簡素化する — 9 機能

| ID | 機能 | おすすめと理由 |
| --- | --- | --- |
| F04 | Codex / Claude 両対応 | 両対応は当面残し、共通の表示・記録と provider 固有の処理を区別する。片方を不要とする根拠は今回ない。新しい provider や比較用機能は実需要なしに増やさない |
| F06 | 中断後の再開 | 再開を利用者が理解できる入口と履歴に整理する。新規実行との区別は残す。provider ごとの既存方針を未使用扱いして一括削除しない |
| F16 | 似た候補の群分け | 一覧を読みやすくする補助として扱う。個々の候補の記録・判定と分け、利用者が判断を追えるようにする。群分けをどれほど使うかは未確認なので、全削除は今の推奨にしない |
| F17 | 一覧・export | 共通の読取結果から、人間向け表示とスキル向け出力を作る形を目指す。同じ状態の解釈を表示先ごとに増やさない |
| F22 | 承認・提出・回答・報酬管理 | 承認した版と宛先の照合は残す。提出後の管理は必要な結果と金額の記録に絞り、外部の管理表と同じ情報を二重入力する運用を避ける。現状も小さい部分があり、大きな削減量は見込まない |
| F24 | 件数・使用量・工数の集計 | 運用判断に使う指標を選び、同じ数字を複数箇所で計算しない。細かな工数入力を任意化する案はあるが、現行の計測規則を変える決定が別途必要 |
| F25 | 状態・診断・通知・復旧 | 状態表示と資源回収を基本にする。通知等は任意の運用補助として分ける。未使用が確認できた補助だけを廃止候補にする |
| F27 | 過去形式の互換性 | 過去データを読む責務に限定する。古い機能の新規実行と混ぜない。Git のコード復元だけで、Git 外のデータや当時の環境まで戻るとは扱わない |
| F28 | CLI | スキル・人間・運用から使う薄い操作窓口として残す。判断や保存順序を CLI 自体へ増やさない。CLI 全削除は代替入口が必要になり、単純な削減とは限らない |

ここでの「簡素化」は、すべての機能に同じ大きさの改修が必要という主張ではない。すでに目指す形になっている部分はそのままでよい。構造の重複と、使わない運用の負担を確認してから対象を絞る。

根拠: [残る Review・CLI の課題](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/blob/2a8e7e25e157e34afbeded94f67f14c090de4991/docs/reviews/2026-10-23-remaining-review-design-issues.md)、[旧記録を読む方針](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/blob/2a8e7e25e157e34afbeded94f67f14c090de4991/docs/adr/0034-harness-control-only-deletions.md)。

## そもそも削除する — 1 機能（移行条件付き）

| ID | 機能 | おすすめと理由 |
| --- | --- | --- |
| F14 | 旧検証方式・シナリオ選択 | 既存の退役方針に従って旧経路を削除する。文章からの手順選択、対象別の旧準備処理、旧 Verifier を並存させ続けると、二つの方式を維持する負担が残る |

これは「今すぐ安全に全削除できると確認済み」という意味ではない。既存の移行受入条件と残る入口の扱いを確認する必要がある。共通の Lab、観測、判定器、証拠保管、過去イベントの読取りは削除対象にしない。今回はこれらの変更や実行は行わない。

根拠: [ADR 0034 の未完了の退役](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/blob/2a8e7e25e157e34afbeded94f67f14c090de4991/docs/adr/0034-harness-control-only-deletions.md)、[ADR 0035 の移行と旧経路](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/blob/2a8e7e25e157e34afbeded94f67f14c090de4991/docs/adr/0035-verification-as-a-skill.md#L42)。

## 判断する順番

1. **F19・F21 の責務を確定する。** 解釈・執筆、決まった条件の照合、保存、人間の最終判断を区別する。すでにスキルが持つ仕事をハーネスに再実装しない。
2. **F14 を退役対象として扱う。** 受入条件が済んでいるかは別途確認する。不要と決まった旧経路を磨き直す計画は立てない。
3. **F17・F28 を整理する。** 同じ記録の読み方と操作窓口にある重複を減らす。既存の記録契約を保つ。
4. **F22・F24・F25 の運用負担を選ぶ。** 管理表との二重入力、細かな工数入力、通知を本当に使うかで残す範囲を決める。

大きく削る選択肢として、片方の provider、常時運転、再開、提出後の管理などを製品の対象から外すことはできる。ただし、それは「使っていないコードの整理」ではなく、今後の運用を変える判断である。今回の証拠だけでは、一律廃止を推奨しない。
