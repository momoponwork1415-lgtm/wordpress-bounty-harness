# bench30（2026-11）: 既知の公開脆弱性 30 件の探索 benchmark

探索の変更を本番の雑音なしで較正するための一覧である（Issue #726）。A/B/C の定義は [docs/reviews/2026-11-01-noticing-vs-reasoning.md](../reviews/2026-11-01-noticing-vs-reasoning.md) の「分類の基準」に従う。この文書には Git に入れてよい情報（slug、版、CVE、型、公開日、インストール数、zip の sha256）だけを書く。答え（修正されたファイルと関数）、zip、展開したソースは Git の外に置く（不変条件 8、#678）。この一覧と答えは探索の入力にしない（不変条件 1）。採点は Trial が終わった後に、台帳と答えを突き合わせて行う。

## 選定の基準

- 出所: Wordfence 履歴 mirror（`history.sqlite`、最新の公開日 2026-10-30）の 2026 年公開記録。1 記録 1 プラグイン、CVE があり、修正版が出ているもの。
- 種類: Programme Boundary 内のものに限る。格納型 XSS、SQLi、ファイル系（任意ファイルの upload / read / delete、LFI、RCE）、認証・権限昇格・ATO 系。反射型 XSS、CSRF、Missing Authorization 単体、情報露出、IDOR、PHP Object Injection、SSRF、2FA 回避、支払い回避は除いた。C は説明文が管理者か任意ユーザーへの到達を書いているものに限った。
- 攻撃者の位置: 題名が「Unauthenticated」か「Authenticated (Subscriber+)」（Customer 同等を含む）のものだけ。Contributor+、Author+、Editor+、Administrator+、Shop Manager や Translator などのカスタムロール前提は除いた（所有者の追加条件、2026-11-01）。
- インストール数: WordPress.org の `active_installs` が 10,000 以上（2026-11-01 に API で確認）。
- CVSS: 各型 10 件のうち 6 件以上を 7.0 以上、残りを 5.0 以上にする（所有者の追加条件）。結果は A 10/10、B 7/10（残り 3 件は 6.4）、C 10/10 が 7.0 以上。
- 公開日: 90 日以内（2026-08-03 以降）を優先した。3 型とも 90 日以内だけで 10 件がそろい、90 日条件も CVSS 条件も緩めていない。
- 版: 影響範囲に入る WordPress.org の版付き tag のうち最も新しいものを「脆弱な版」、記録の最初の修正版を「修正版」にした。30 件とも 2 つの版の間に別の tag は無い。zip は `https://downloads.wordpress.org/plugin/<slug>.<version>.zip` から取得した。
- 1 件 1 プラグイン。30 件の slug はすべて異なる。

## 除外

- 自分たちが Wordfence に提出したプラグイン（#678）: wp-seopress、mailerlite、check-email、custom-twitter-feeds、otter-blocks、admin-columns、iubenda-cookie-law-solution、vk-blocks、buddypress、anywhere-elementor と dynific 系、fluentform、ninja-tables、pods、depicter、wp-ulike、breeze、optimole-wp、acf-extended。
- 所有者（Yuto Hyakumoto、momopon1415）が研究者に入っている記録。所有者の実績は非公開の set として別に数える。

## 型の判定

型は **題名と説明文からの推定** である。A は要求の値が型どおりの sink に届くもの（SQLi、ファイル系）、B は低権限者が保存した値が別の画面で描画される格納型 XSS、C は権限昇格・認証回避・ATO とした。修正差分を読んで型がずれて見えた件は、Git 外の答えの `notes` に書いた。型を差分で付け直すときは、この一覧と答えを同じ変更で直す。

## 採点の手順（読み取り専用）

### Trial の回し方との対応

- 1 件につき、脆弱な版で 3 Trial、修正版で 1 Trial を回す（Issue #726）。各 Trial は別の campaign にし、campaign id に benchmark の接頭辞を付ける（例: `bench30-<slug>-vuln-1`、`bench30-<slug>-fixed-1`）。benchmark の campaign は選定を通さず、funnel の分母に入れない。
- 答えの JSON はどの Trial にも渡さない。採点は、その case の全 Trial が終わってから行う。

### 突き合わせ

1. campaign と case の対応表を Git 外に作る: `{"<campaignId>": {"cve": "CVE-...", "arm": "vulnerable" | "fixed"}, ...}`。
2. `node --no-warnings score.mjs --state <state> --map <map.json>` を実行する。スクリプトは `<state>/ledger.sqlite` を `readOnly` で開き、campaign ごとに `finding-recorded`、`finding-parked`、`lead-recorded` を読む。各 event の `artifacts` の `finding`（`lead`）の digest から `<state>/private-evidence/<digest>/content/finding.json`（`lead.json`）を読み、`sourceTrace` の各 frame の `file` と `function` を答えと比べる。台帳にも Private Evidence にも書かない。
3. 比べ方:
   - ファイル: 先頭の `/workspace/main/`、`./`、`<slug>/` を外した相対パスが答えのファイルと一致するか、どちらかが他方の末尾に一致すれば当たり。
   - 関数: `Class::method`、`->method`、`.method` の最後の名前を小文字にして、答えの関数名と一致すれば当たり。
4. 判定:
   - **ソース水準の再発見**: 脆弱な版の Trial の Finding（`finding-recorded` か `finding-parked`）の `sourceTrace` が、答えのファイルか関数に 1 frame でも届いたもの。関数まで届いたものは「関数水準」として別に数える。
   - **pass@3**: 脆弱な版の 3 Trial のどれかで再発見があれば、その case は 1。型ごとに「pass@3 の case 数 / 10」を出す。
   - **Lead だけ**: Finding では届かず、Lead の `sourceTrace` だけが届いた case。再発見には数えず、別の列で出す。
   - `incomplete` で終わった Trial と、artifact を読めなかった Finding（`missingArtifacts`）は、再発見なしに混ぜない。Trial 数と一緒に報告する。
5. スクリプトの当たりは候補である。impact の種類が記録と同じか（例: SQLi の case で SQLi の Finding か）を、Finding の `impact` と `claim` を読んで AI が確かめ、違えば当たりから外す。外した件数も報告する。

### 修正版での偽陽性の数え方

- 修正版の Trial の Finding のうち、`sourceTrace` が答えのファイルか関数に届き、impact の種類が記録と同じものを **偽陽性** に数える。修正済みの箇所を、修正前と同じ主張で報告したことになるからである。
- 型ごとの偽陽性率は「偽陽性が 1 件以上あった case 数 / 修正版の Trial を回した case 数」とする。Finding 単位の件数も併記する。
- 修正版の Trial で、答えの場所に届かない Finding は偽陽性に数えない。未知の脆弱性か別の誤りかは benchmark では判定できないので、「修正版のその他の Finding」として件数だけ出す。
- 修正版の Trial が `incomplete` なら、その case は偽陽性率の分母から外し、外した数を書く。

### 報告に書くもの

型ごとの pass@3 再発見率、関数水準の率、Lead だけの case 数、修正版での偽陽性率、1 件あたりの Codex 時間（`discovery-run-finished` の wall）。Issue や PR には件数と CVE だけを書き、答えのファイル名・関数名・Finding の本文は書かない。
