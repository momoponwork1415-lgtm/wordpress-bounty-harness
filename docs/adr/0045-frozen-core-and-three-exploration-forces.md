# 変えないものを 5 つ凍結し、探索を 3 つの戦力に分ける（#724）

## 背景

本リポジトリは 2026-10-16 の本番開始から 2 週間で、探索 mode を 2 つ作って 2 つ廃止し（区画分配、一発 run）、探索プロンプトを 5 回替えた（v14 → v16 → v17 → v18 → v14 → v19）。その間に本物の率（段 1b を通る Finding / Trial）は 0.05〜0.07 で動いていない。過去 4 世代も同じ型で止まった（LESSONS 14）。所有者は 2026-10-31 夜に「もうこれだけは絶対に変えないものを決めておきたい」「今 1 つにまとまっているものを分割しよう」と決めた。

変えすぎた原因は記録から 5 つ読める。

1. 1 Trial あたり 0.2〜0.8 件の Finding を 20 Trial で比べていて、同じプロンプトを 2 回回しても同じ差が出る粒度だった（[ギャップ分析 第 4 節](../reviews/2026-10-28-harness-gap-analysis.md)）。
2. 数えていたのが Finding の数で、本物の率ではなかった。Finding の数は文面で動くが、本物の率は動かなかった。
3. Wordfence の結果（受理、重複、対象外）が設計の判断に入っていなかった。台帳に結果を記録し始めたのは 2026-10-31 である（#703）。
4. 公開の設計（Argus、PRISM、区画分配）を部品ではなく丸ごと持ち込み、数字が出る前に次を作った。
5. AI が設計案を安く出し、所有者が速く go を出し、提案から実装まで数時間だった。

一方で、Snapshot と digest、gVisor、台帳、Lab、人間の観測、提出の流れは一度も崩れず、この土台の上で 2 週間に CVE 級の 5 件（Validated 4、審査中 1）と報酬 1 件が出た。

## 決定 1: 凍結する 5 つ

以下は、所有者が自分の言葉で改めると言うまで変えない。AI は変更案を出さない。

| 凍結するもの | 理由 |
| --- | --- |
| **確定は、人間が Lab で観測したものだけ。** 判定器、AI の自己申告、捕捉を読んだ推定は根拠にしない。所有者はコマンドを打たず、AI 操作役が所有者の発言から記録する（ADR 0040 追記 3・4） | 不変条件 3 は 2 週間で 3 回書き換えた。今の形で止める |
| **Harness は制御だけを受け持つ。** 探索と検証の中身はプロンプトとスキルに置く（AGENTS.md「Harness と AI の責務」） | 過去 4 世代の死因 |
| **台帳は追記専用で、digest 参照だけを持つ。Private Evidence は Git の外**（不変条件 8） | 事故で失うと取り返せない唯一のもの |
| **設計を判断する分母は 1 つ。** Codex 1 時間あたりの Lab 発火数と、Wordfence の結果（受理、重複、対象外、却下）。Finding の数と Lead の数は観測として記録するが、採否の根拠にしない | 原因 1〜3 を同時に塞ぐ |
| **設計の変更は月 1 回まで。** 変える前に、Issue に測る数字と採否の線と消し方を書く。探索プロンプトの文面は、消す方向にしか触らない。言い換えの新版は出さない | 原因 4〜5 を塞ぐ |

凍結しないもの: 選定の帯、子の数、制限時間、掃き出しの規則、スキルの中身、Lab の構成。これらは数字で動かす部分である。Snapshot と digest、gVisor、人間による提出は不変条件 1・2・7 にすでにあり、一度も揺れていないので、ここには重ねて書かない。

## 決定 2: 探索を 3 つの戦力に分ける

今の「選定が選んだプラグイン 1 本に 2 時間の wide Trial」を主経路から降ろし、次の 3 つに分ける。設計は [#724](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/issues/724) にあり、段階と数字もそこに置く。

1. **掃き出し。** 上位プラグインの固定ソースに規則を当て、ファイル・行・入口・sink の候補行を出す。規則は型の規則（SQLi の連結、格納型 XSS の sink、identity の sink 一覧）と、自分の確認済み Finding から書いた変種の規則。公開記録は入力にしない（不変条件 1、ADR 0012）。候補 1 行に短い子を 1 体当てて chain を完成させ、既存の出力契約で Finding か Lead にする。
2. **差分監視。** 上位プラグインの新版が出たら、差分だけを掃き出しの規則に通し、新しい identity・決済・入力処理のコードを候補の先頭に置く。所有者は 2026-10-31 に「差分は入れるつもり」と明言した。
3. **名指しの深掘り。** identity の sink を持つ大型プラグインに限り、名指しで今の wide Trial（と ADR 0044 の Lead 入力 Trial）を立てる。

責務の境界は変えない。Harness が持つのは「規則を走らせて候補を保存する」「候補ごとに子を立てる」「差分を取る」の制御だけで、規則と読み方は skill のディレクトリに置く AI の内容である（ADR 0043 の置き方）。

根拠: 所有者の Wordfence 記録 32 件のうち SQLi と格納型 XSS が報酬の 58% で、入口を機械で列挙できる。10 / 32 件は修正版の後に同じプラグインへ戻って見つけたもの。公開手法を語る上位ハンターは全員が「安い機械の絞り込み → AI の確認 → 実環境の再現」の順で、入口は掃き出しか差分監視である（[調査](../reviews/2026-10-31-owner-record-types-and-architecture-fit.md)、[2026-10-25 の調査](../reviews/2026-10-25-wordpress-bug-hunter-methods.md)）。

この分割が 2026 年 11 月の 1 回の設計変更である。11 月中は、#724 の段階（PR 1〜4）以外の探索の設計変更を出さない。

## 理由

変えすぎの原因は、測る分母と変える頻度にあった。凍結の 5 つは、動いていない土台を名指しして守り、分母と頻度を固定する。3 つの戦力は土台を変えず、入口だけを「選定が選んだプラグイン」から「規則と差分が指した場所」へ替える。失敗しても revert で元に戻る。

## 採らなかった選択肢

- 不変条件 1〜8 をそのまま凍結の一覧にする: 不変条件 3 は 3 回変わった。「今の形で止める」と書かないと、また動く。
- 探索プロンプトの文面も凍結する: 消す方向の変更（stale な判定器の記述など）まで止まる。消すだけは許す。
- 3 つの戦力を v19 の計測後に始める: 所有者が 2026-10-31 に開始を決めた。v19 の 20 Trial は並行して終え、分母の基準線として使う。
- 2 時間の wide Trial を削除する: identity の sink を持つ大型プラグインには深掘りが要る（TranslatePress の ATO は深掘りで 2 度再発見した）。名指しに降ろすだけにする。

## 帰結

- SPEC 第 2 節の末尾と AGENTS.md に、この ADR の凍結の 5 つへの参照を 1 行ずつ足す。別 PR。
- ADR 0029 の「単一協調 Trial を主経路とする」と ADR 0039 の「wide を既定の mode とする」は、3 つの戦力が本番で動いた時点で「名指しの深掘り」の記述に改める。それまでは今の運転を続ける。
- #724 の PR 1（掃き出しの規則 1 本、Trial は立てない）から始める。採否の線は #724 のとおり、2 週間で Lab 発火 0 なら消す。
- DEVELOPMENT.md 第 5 節の採否 6 段は、分母を「Codex 1 時間あたりの Lab 発火数」に合わせて改める。別 PR。

## 消し方

この ADR の PR を revert する。凍結の 5 つは文章なので、戻せば元の運用に戻る。3 つの戦力は #724 の各 PR を revert する。台帳には既存の event しか増えない。
