# 人間と判定器の役割分担を、所有者の作業時間を目的関数にして固定する（分類ごとの受理基準と再現の形を Harness が持つ）

## 背景

所有者は旧ハーネス（候補を人間が全件読んで採否し、手で再現）で報奨を得ていた。新ハーネスの目的は、発見数を旧と同等に保ちながら所有者の作業時間を減らすこと（所有者、2026-10-11）。報奨になった7件は Stored XSS 4、SQLi 2、ATO 1、すべて未認証。所有者の追加の指摘（2026-10-11）: 手動再現自体は手間ではない。困るのは分類ごとの成立基準と PoC の形が無く、Finding ごとにばらばらになること。判定器は無くてもよく、攻撃を再現する標準形の Python スクリプトで代替できる。

[徹底設計レビュー](../reviews/2026-10-11-thorough-design-review.md) 第13節は、現状では人間の時間が旧より増えると判定した。理由は、判定器が届かない Finding が診断付きで人間に渡ること、`incomplete` に機械の前処理が無いこと、`contradicted` が自己申告で出て人間に見えないこと、判定器の無い分類が出口の無い工程として残ること、confirmed でも手動再現が全件必須であること、人間の時間を測る項目が台帳に無いこと。

## 決定

### 1. 分類ごとの受理基準と再現スクリプトの形を Harness が固定する（所有者の決定、2026-10-11）

- 所有者が困っているのは手動再現の手間ではなく、「この分類なら何を観測すれば成立とするか」と再現スクリプトの形が Finding ごとにばらばらなこと。判定器は「あれば使う」であり、必須ではない。
- profile に、影響分類ごとの **受理基準（Acceptance Criteria）** と **再現パッケージの雛形** を版・digest 付きで置く。受理基準は SPEC §8b の判定器成功条件と programme の受理・却下条件（SPEC §8a）から導き、新しい条件を発明しない。雛形は全分類で同じ骨格を持つ: 前提設定、使うロール、手順、期待する観測、修正版での負の対照、提出先ごとの受理条件の充足欄。
- 再現スクリプトは標準ライブラリと `requests` だけで動く1本の Python に固定し、入口（Lab URL、認証情報、nonce の受け口）と出口（観測結果の構造化出力）を Harness が決める。Verifier はこの形に埋める。形に合わない出力は `incomplete(recipe)`。
- 検証の状態を3つにする。`runtime-confirmed`（判定器が canary を観測。ADR 0004 のまま）、`reproduced`（判定器の無い分類で、Harness が新しい Lab で標準形スクリプトを実行し、期待する観測が構造化出力に現れ、修正版で現れない）、`incomplete`。`reproduced` は提出候補になれるが、人間の手動再現と受理基準の充足確認を経るまで Submission Candidate にしない。
- `runtime-confirmed` の定義は変えない（不変条件3）。`reproduced` はスクリプトの自己申告ではなく、Harness が実行し Harness が捕捉した HTTP と構造化出力を根拠にする。捕捉が無い、または出力が期待観測を含まないときは `incomplete(observation)`。
- 判定器のある分類でも、再現パッケージは同じ雛形で出す。判定器は雛形の「期待する観測」欄を機械で埋める追加の証拠であり、別の経路ではない。

### 2. 人間が見る列は confirmed と、機械の手が尽きた incomplete だけ

- `runtime-confirmed`: 再現パッケージ付きで列に出す。
- `incomplete`: ADR 0022 の理由別再試行が尽きた後にだけ列に出す。`recipe` と `observation` は再試行の上限に達するまで人間に見せない。`provision` は再供給1回の後。`precondition` は catalogue に次の scenario ID が無いときだけ。`evidence`、`cleanup`、`digest-mismatch` は即時に出す（Harness 側の欠陥の疑いがあり、人間の判断ではなく修正の材料）。
- 列の既定表示は campaign ごと・理由ごとの集計。Finding 単位の表示は、人間の判断が要る理由（`precondition` で scenario が無い、`evidence`）に限る。
- `contradicted`: 件数だけ。ただし `contradicted` を出せるのは、修正版の負の対照で Harness 捕捉の再実行が判定器を鳴らさなかったときに限る。原 Finding に対して Verifier の反証文だけで `contradicted` を出す経路は `incomplete(observation)` に変え、反証文の digest は補助資料として添付する（不変条件4、レビュー H1）。

### 3. 人間の作業は「読む」「手で再現する」「提出する」の3つ。それ以外は Harness（所有者の決定、2026-10-11）

- 所有者の作業は、再現パッケージとレポート文案を読むこと、パッケージの手順を自分の手で再現すること、提出先の画面で提出して転帰を記録すること、の3つに限る。候補の採否、Lab での再現実行、重複照合、文案の生成、Lab の再構築は Harness が行う。
- 手動再現は全件必須。Harness も新しい Lab で標準形スクリプトを実行し、捕捉した HTTP、観測した効果、画面画像をパッケージに入れるが、それは人間の再現を省く根拠ではなく、人間が再現するときの照合先である。人間の再現結果（一致 / 不一致 / 再現不能）は台帳に記録し、不一致はパッケージ生成器か基準の欠陥として扱う。
- 人間が手で再現する Lab は Harness が setup manifest から1コマンドで立てる。人間が Lab の構築や設定を手でやる工程は置かない。
- 読む順番と再現の手順は雛形で固定する: (1) 受理基準の充足欄、(2) 期待する観測と実際の観測、(3) 負の対照、(4) 手順。分類が違っても同じ順番で読み、同じ形で再現できる。
- 再現パッケージの各項目に出自（`harness-captured` / `agent-authored`）を付け、agent 作成物は補助ファイルに分ける。人間が判断と再現に使うのは Harness 由来の項目、充足欄、手順。
- レポート文案は Harness が雛形と Harness 由来の証拠から生成し、提出先の入力形式に合わせる（#95）。重複照合も提出前に Harness が行い、結果と照合時刻を文案に添える（#96）。人間は文案を直してよいが、新しい証拠を文章で足さない。
- Harness 捕捉が無い Finding はレビュー列に出さない。負の対照が取れない Finding は、その旨を充足欄に明示する。

### 4. 人間の時間を台帳で測る

- 人間の作業ごとに1 event を追記する: `human-effort-recorded { campaignId, findingId?, action, minutes, snapshotDigest }`。`action` は `read` / `reproduce` / `submit` / `outcome` の4値。CLI の各 review 副コマンドが終了時に分数を尋ねて記録する。
- 指標は2つ。提出1件あたりの所有者分数（読む・再現する・提出する・転帰を記録する、の合計。分母は `submission-recorded`）、提出1件あたりに人間が開いた Finding 数。campaign ごと・分類ごとに `ledger funnel` に並べる。
- 基準値は旧ハーネスでの所有者の見積り（提出1件あたりの分数）。所有者が1行で記録し、`docs/records/` に日付付きで置く。目標は基準値の半分。

## 理由

- 旧で時間を使ったのは「偽物を見分ける」と「手で再現する」の2工程。前者は判定器に移し、後者はパッケージの出自で要否を決めることで、判定器が決定論的であることを時間に還元する。
- 判定器を必須にしないのは所有者の判断。旧ハーネスで報奨に至った工程は「新しい環境で recipe を実行し、人間が再現する」であり、`reproduced` はそれを Harness の実行と捕捉、固定の基準、固定の形で規律化したもの。判定器は追加の証拠として残す。
- 分類ごとの受理基準と雛形を固定するのは、人間が毎回「何を見れば成立か」を考え直す時間を無くすため。基準は programme の条件から導くので、提出時の却下条件の確認と同じ作業になる。
- `incomplete` を集計で見せるのは、形式失敗の診断を人間から外すため。Finding 単位で見せる理由を限定し、人間が見るのは判断が要るものだけにする。
- `contradicted` の限定は、人間が見ない状態に候補を落とす唯一の経路を Harness の観測に限るため。

## 採らなかった選択肢

- 判定器の無い分類を提出対象外にする: 当初の所有者判断（同日）だったが、標準形スクリプトで代替できるという指摘で撤回。発見の幅を判定器の実装順に縛らない。
- `reproduced` をスクリプトの自己申告で出す（旧 recipe 方式）: ADR 0004 が退けた理由のまま。Harness の実行と捕捉を根拠にする。
- 人間の手動再現を省く、または抜き取りにする: 所有者が全件必須と判断（同日、一度揺れた後に確定）。再現の手間は目的関数に入らず、却下の責任が所有者の口座に残るため。
- `incomplete` を Finding 単位で全件見せる（現行）: 診断の時間が人間に戻る。

## 既存決定との関係

- ADR 0002 の「人間は confirmed と次手付き incomplete を見る」を、「confirmed と、機械の手が尽きた incomplete の集計」に置き換える。人間ゲートが2つであることは変えない。
- ADR 0004、不変条件3は変えない。`runtime-confirmed` は判定器だけが出す。`reproduced` は別の状態であり、`runtime-confirmed` と混ぜない。SPEC §7 の結果3値に `reproduced` を加え、不変条件3に「`reproduced` は Harness が実行・捕捉した標準形スクリプトの観測だけを根拠にする」を補う。
- ADR 0010 の「programme scope は検証を止めない」は維持する。受理基準の充足欄は scope 評価の入力であり、検証の停止条件ではない。
- ADR 0022 の再試行方針を、人間に見せる条件として使う。`no-judge` の行は「人間へ回す」から「集計のみ」に変える。
- ADR 0015 の Harness 捕捉を、再現パッケージの出自と `contradicted` の条件の根拠にする。
- SPEC の変更箇所: §7「判定器を定義できない種別は…人間へ回す」、§7 再現パッケージの内容、§8「レビュー列に出すもの」「人間が決めること」、§9 のイベント例に `human-effort-recorded`。

## 帰結と受入条件

- 実装順: (1) `contradicted` の限定、(2) 分類ごとの受理基準と再現パッケージ雛形を版・digest 付きで profile に置く、(3) 標準形スクリプトの入口・出口を固定し Harness が実行する `reproduced` を verification に足す、(4) レポート文案の生成（#95）と重複照合（#96）を提出前の機械工程にする、(5) ADR 0022 の再試行、(6) パッケージの出自分離と読む順番、(7) `human-effort-recorded` と funnel の2指標。人間の作業が「読む・再現する・提出する」だけになる状態は (4) まで揃って初めて成立する。
- `incomplete(no-judge)` は (3) 以降は発生しない。判定器が無ければ `reproduced` の経路へ進む。
- 受入条件: 本人発見7件の再発見（#127）で `runtime-confirmed` または `reproduced` になった Finding について、7件が同じ雛形で読めること、受理基準の充足欄が人間の判断と一致した率、手動再現の一致率、提出1件あたりの分数を台帳から出し、所有者の旧基準値と並べる。
- 分類ごとの受理基準と雛形は、7件の分類（Stored XSS、SQLi、ATO）を先に書き、残りは `no-judge` の件数が出た分類から足す。
- この ADR は状態、列、雛形の骨格、記録の規則だけを決める。受理基準の本文、雛形の各欄の文言、スクリプトの入口・出口の仕様は profile の版付き文書として別 PR で書く。判定器の到達率（レビュー H3、H4、V-F13）は `reproduced` の経路ができれば提出の前提条件ではなくなる。
