# テスト戦略

目標は「533テストが緑」ではなく、最新版の対象で偽の報告を出さず、実際の発見を証拠付きで人間へ渡せること。Matt Pocock の TDD でいう公開 seam（外から振る舞いを観測できる境界）を使い、実装の内部関数をなぞるだけのテストを増やさない。各縦断Issueでは、先に失敗する受入試験を1つ置き、最小実装で通す。

## 境界と、何を証明するか

| 公開 seam | 必須の試験 | これだけでは分からないこと |
| --- | --- | --- |
| `campaign run` と台帳 | 固定SnapshotでRoot＋3の子の成果が独立記録され、1人が失敗しても有効なFinding/Leadが消えない。provider limit後の再開で二重登録しない | モデルの発見能力 |
| Discovery reportの受入 | 最終JSONに不正候補が混じっても有効候補を保存し、不正分は理由を残す。全体の整形失敗を「0件」と記録しない | 候補が本当に脆弱か |
| `verify` とHarness判定器 | 新しいLabのnonce canaryだけが `runtime-confirmed` を出す。修正版・異なるSnapshot・証拠欠落は正しい結果型になる | 実際の提出先が受理するか |
| `review` とPrivate Evidence | 最新版の確認、重複の鮮度、英語レポートJSON、HTTP/画像/canary証拠、人間Lab手順が揃うまでSubmission Candidateを提出可能にしない | 人間が再現できる説明か |
| `select` | 低権限・高影響履歴、install数、対象範囲を根拠付きで順位付けし、feedが古い時は明示する | 将来の当たり率 |

## 4段の品質ゲート

1. **毎変更:** `pnpm check`（型、整形、公開seamの振る舞いテスト）。候補の受入、digest不一致、`incomplete`、追記専用の境界はここで守る。
2. **実環境の統合:** 固定imageの `runsc`、WordPress/MySQL、broker、低権限HTTP、canary捕捉を使う。providerは記録済み応答または小さな実呼出しに分け、ネットワークの不調とコードの退行を区別する。
3. **TranslatePressの本番開始ゲート:** 3.2.6 Stored XSSをRoot＋3で1回試し、ゲートを通らなければ診断後に3.3.1アカウント乗っ取りを1回試す。片方でsource根拠付きFinding→新しいLabのnonce判定器→同じ経路の修正版対照を通せば本番へ進む。子の成果と費用も保存する。公開事例の答え、修正差分、PoCは探索入力へ渡さず、人間のAnswer Key入力も要求しない。上限と保留時の診断は[ベンチマーク計画](TRANSLATEPRESS-BENCHMARK.md)。
4. **最新版の本番パイロット:** 最小自動選定で公開最新版3対象を探索する。成果0件でも正常完了・証拠の保持・費用記録が動くことを確認する。実Findingが出たら最新版の独立検証、重複・scope照合、英語文案、人間の手動Lab再現、承認を提出ゲートとして通す。発見率や報奨はその後の前向き記録で評価する。

## 故障を注入する箇所

provider上限、子agentの途中失敗、最終JSON破損、Lab起動失敗、proxy証拠欠落、別digestのFinding、Wordfence feedのstale、最新版の変更、再現パッケージの欠落をそれぞれ試す。正しい帰結は「黙って0件」「偽のconfirmed」「未承認の送信」ではなく、理由付きの `incomplete` または実行停止である。

## 成果の読み方

開発セットの再発見は配線と判定器の受入試験であり、未知脆弱性の発見率ではない。A/Bとpass@kは同じモデル、対象、source、予算、判定器、提出範囲を固定して初めて比較する。小さい標本では件数・区間・使用量を併記し、差が示せない時は「判定不能」と記す。
