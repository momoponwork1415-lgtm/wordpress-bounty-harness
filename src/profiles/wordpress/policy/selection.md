# WordPress 対象選定方針

正本の設定は [selection.json](selection.json)。`loadWordPressSelectionPolicy()` で読み込む。

- 本番の `candidateSource` は WordPress.org の人気順（`browse=popular`）だけを列挙する。タグの一覧は 2026-11-01 に外した。人気順はインストール数の降順で全プラグインを並べるので、下限以上の対象はタグ無しで全部拾える（2026-11-01 の実測: 8 タグが足した候補は 0 件）。一覧の数を減らすのは、1 本でも取得に失敗すると候補全体が空になる規則を安全側に保つためでもある。`tags` に語を書けばタグ順の列挙も従来どおり動く。取得元、観測時刻、応答 digest を記録し、取得不能・期限切れの一覧からは候補を採らない。`candidateSlugs` と `pinnedVersions` は開発対象を手動固定する旧形式として残す。両形式は union で分ける。選定の適格性と順序は `select(policy)` が機械的に決め、人間の対象承認は置かない。
- 操作者が作った候補一覧は、自動選定方針の任意欄 `operatorCandidates` に `{ "slug": "synthetic-example", "version": "1.2.3", "evidenceDigest": "sha256:ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff" }` の配列として足し、ランナーの選定で取り込む（[#520 の限定承認](https://github.com/momoponwork1415-lgtm/wordpress-bounty-harness/issues/520#issuecomment-6468469367)）。例の digest は合成値で、実際には操作者が Git 外に保管した根拠の SHA-256 を指定する。
- 候補一覧は一覧取得が成功したときに通常の候補へ統合し、同じ slug は 1 回だけ観測する。候補一覧内で重複する slug と、slug・version・evidenceDigest 以外の欄は拒否する。本文や file path は受け付けず、根拠 digest の本文を選定器が開くこともない。
- 候補一覧の指定版は観測した stable と完全一致する必要があり、不一致なら `operator-candidate-version-mismatch` でその回の対象から除く（通常一覧にも同 slug がある場合を含む）。歴史版へ固定せず、別の版へ読み替えない。適格性・install 順・同版 1 Trial の条件は通常候補と同じで、候補一覧による優先枠は置かない。
- 候補一覧は方針 digest に束縛し、観測した候補の slug・指定版・根拠 digest は既存 `selection-report.json` の `inspections[].operatorCandidate` に残す。探索へ渡す `TargetSelection` に根拠参照や本文は含めない。種生成、sweep skill、機構文・修正差分本文の探索入力は未実装で、本取込みの範囲に含めない。
- 人気順と各タグの一覧は、インストール数が下限を割るページか API の最終ページまで読む。固定のページ数・候補数の上限は新設定から外す。取得失敗や API のページ上限で切れた母集団は `unavailable` とし、部分的な列で尽きたとは判定しない。
- 必須pluginは対象のメインPHPファイルの `Requires Plugins` ヘッダから取得する。同じ先頭8 KiBに `WC requires at least:` または `WC tested up to:` が値付きであれば、`woocommerce` を依存に足す（`Requires Plugins` と重複しても1件。WooCommerce自身は自分に依存しない）。ヘッダは必須と任意の連携を区別しないので、任意連携の対象にも WooCommerce が入る。ただし版の固定だけで依存を決める方針（`candidateSlugs` の方針と reverify。`dependencyVersionPolicy: pinned-only`）では、WC の版ヘッダだけから決めた `woocommerce` は任意の依存とする。`pluginDependencyPins` に版が無ければ Snapshot に入れず、依存の pinset に `skippedDependencies`（理由 `header-derived-unpinned`、宣言した slug）を残す。`Requires Plugins` や `pluginDependencySlugs` で名指しされた依存は、固定が無ければ `unpinned-required-plugin` で止める。どちらのヘッダにも現れない依存は選定方針の `pluginDependencySlugs` に対象slugごとに明示する。本番の自動選定では `pluginDependencySlugs` にslugを挙げ、freeze時点の公式stable版を固定する。現行 Unlimited Elements はヘッダが依存を宣言しないため、既定方針で Elementor を指定する。手動の開発・歴史的評価は `pluginDependencyPins` に版を指定する。過去の評価対象に用いた Unlimited Elements 2.0.16 の Elementor 4.2.0 の固定（2026-11-01 に削除した `docs/evaluation/public-source-pins.json`、tag `archive/pre-docs-rewrite-2026-11-01`）は現行版の既定値へ流用しない。取得失敗時に依存を省略して探索やLabを起動しない。依存の指定変更は選定方針digestを変え、Snapshotには取得した版とsource digestが残る。
- 本番はインストール数 5,000 以上（2026-11-01 に 10,000 から下げた。人気順の 99 ページ限界は約 2,000 インストールなので、その内側）、180 日以内に更新された対象を選ぶ（2026-11-01 に 365 日から縮めた。181〜365 日の帯は母集団の 7% で 2026 年の記録の 1%）。1 バッチは上限の 10 件。cascade は使わない。インストール数の降順、同数なら更新日の降順に並べる（ADR 0037 の 2026-10-28 追記）。WordPress core 版は、方針にも campaign 設定にも書かない。選定が WordPress.org の `core/version-check/1.7` で最新の安定版を読み、host 設定の Lab image の版と比べる。同じなら image の版で Snapshot を作る。違えば何も凍結せず `core-image-outdated` を返し、ランナーは image が更新されるまで待つ（#741、ADR 0048）。開発・歴史的評価だけ `wordpressVersion` を書いて固定する。
- 順序は `ordering` で決める。本番は `install-band-then-published`（インストール数の帯 `orderingBands`（既定 100 万 / 10 万 / 1 万）の高い帯を先に、帯の中では stable 版の公開日が新しい順、同日はインストール数の降順、同点は slug。所有者決定 2026-11-01 夜、ADR 0037 の 2026-11-01 追記 4）。`version-published` は帯を置かずに公開日順だけにする値（追記 3）。`installs`（インストール数の降順、同数は公開日の新しい順）は鍵を省いたときの既定で、過去の方針と `candidateSlugs` の開発用方針はこれで読む。版上昇で戻った対象も同じ順序に入るので、新版は出た直後に列の先頭に来る。
- 選ばないもの：WordPress.org 非掲載、観測不能、観測期限切れ、配布停止。配布停止は理由コード `distribution-closed` で区別する。
- `excludedAuthors` は、公式プログラムの対象外資産（Automattic、Facebook、Google、SiteGround、Yoast）の作者を除く。WooCommerce 名義と MailPoet 名義の plugin は Automattic 資産なので `WooCommerce` と `MailPoet` も入れる（2026-10-17。本番 batch 5 で google-listings-and-ads と woocommerce-payments が選ばれた抜けの修正）。作者情報が取れない対象は適格にしない。
- `excludedSlugs` には、作者名だけでは所有関係を断定できないものと、ベンダー側のweb serviceが無いと動かないものを手で入れる。後者はメタデータから機械的に判定できないため、タグからは推定しない。
- `maximumTargets` は 1 バッチの上限。台帳の Trial が同じ版か上位の版を既に調べていれば外し、新版なら日数を待たずに戻す。未提出 Finding と旧世代の履歴では除外しない。探索が始まらなかった run と provider 上限からの再開は SPEC 第 6 節に従う。別ランナーが予約中の対象と同版の凍結失敗は従来どおり外す。次の campaign は最新の選定バッチに固定された対象と Snapshot を使う。
- `maximumObservationAgeDays` と `maximumUpdateAgeDays` は別々の鮮度制限。Wordfence programme 方針の観測も `current` である必要がある。
- 選定は Wordfence ミラーを開かず、履歴の採点と鮮度 gate を持たない。ミラーは `wbh-screen` と `wbh-dedupe` で使い続ける。重複は提出前に照合する。
- `maximumActiveInstallations` は任意のインストール数の上限で、値は含まない（観測したインストール数がこの値以上の候補は選ばない）。`minimumActiveInstallations` より大きい正の整数だけを受け付け、同じか小さければ読み込みで拒否する。鍵が無ければ上限は無く、従来と同じ選定になる。上限以上の候補は観測したうえで `selection-report.json` の `inspections[]` に理由コード `above-maximum-installations` で残し、`maximumTargets` には数えない。人気順の列挙は上限とは無関係に先頭（100 万以上）から読み、下限を割るページで止まる。版上昇の再訪にも特別な扱いは無く、上限以上の plugin は候補にならないだけである。所有者決定 2026-11-02 夜「それならやっぱり1〜100万の間に使用」: 2026-11-01 batch 3 以降の本番は帯優先の先頭から ≥1M 帯だけを回していた。prod-v21（v21-wide、2026-11-01→02）の数字は 100k–300k 帯 10 Trial → Finding 3 / Lead 19（0.30 F/Trial）、≥1M 帯 59 Trial → Finding 2 / Lead 122（0.03 F/Trial）。本番の Git 外の方針に `maximumActiveInstallations: 1000000` を置いて 1 万〜100 万の帯に戻す（ADR 0037 の 2026-11-02 追記）。repo の `selection.json` は変えない。
- `cascade`、`scoreWeights`、`history*`、`maximumHistoryAgeDays`、`revisitPolicy.minimumDaysSinceTrial` は新方針で拒否する。`revisitPolicy` は `version-increased` だけを受け付ける。任意の `revisitPolicy.countTrialsFrom`（ISO 時刻）より前に始まった Trial は「探索済み」に数えない。探索の方法（目的文、スキル、mode、Lab）を変えて再開するとき、操作者がその再開時刻を入れ、旧方法でしか調べていない版を列に戻す（所有者決定 2026-11-01、ADR 0037 追記 6）。Lab の失敗と凍結の失敗の除外は、この時刻に関係なく従来の規則で残る。repo の方針には書かず、本番の Git 外の方針 file にだけ書く。旧 `target-selection.json` のスコア内訳、履歴、`cascadeStep`、`highThreatSurface`、`runBudget` は読めるまま残す。
- 選定記録はインストール数、更新日、`reason: initial | version-increased` と方針 digest・観測 ref を残す。理由は既存 `target-selected` の artifact digest から読める。既存イベントの型は変えない。
- 旧方針の `runBudget` も 2026-10-19 に削除した（古い `target-selection.json` の `runBudget` は読み続ける）。run 数は対象ごとに 1 Trial である（ADR 0029。増やす `campaign run --repeat` は 2026-11-05 に削除した）。選ばれた対象を指名したタグは `candidateTag` に残り、半年後にタグ別の有償率を測る材料になる。
